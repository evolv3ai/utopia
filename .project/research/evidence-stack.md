## Finding: S2 — Each of the three "no single uuid" targets has a uuid already in the schema, with different stability

- **Claim**: (a) An ontology proposal row has `id UUID PRIMARY KEY` and `UNIQUE (kb_id, section, key)`. The agent's refresh is `ON CONFLICT (kb_id, section, key) DO UPDATE … WHERE ontology_proposals.status = 'open'`, which never changes `id` and never re-opens a decided row, so one `(kb, section, key)` has one row id for life. No store reader returns it: `StoredProposal` has no `id` and both `open_proposal` and `open_proposals` select `section, key, payload, proposed_by, serves, signatures`. (b) A kind-word binding has `id UUID PRIMARY KEY` and `UNIQUE (kb_id, kind_word)`, but the id is not a stable name for the word: the person's decision is an upsert that inserts a fresh `Uuid::now_v7()` when no row exists, `type_id` is `REFERENCES entity_types(id) ON DELETE CASCADE` (deleting the class deletes the binding row), the `Binding` struct carries no `id`, the stored word is normalized (`normalize(kind_word)`), and the session handler writes its audit row with target id `None`. (c) A run targets the base, whose id is the `kb_id` every ledger row already carries.
- **Source**: `migrations/0004_ontology.sql:60-82`; `crates/utopia-store/src/ontology.rs:1912-1920, 1943-1947, 2003-2030`; `migrations/0065_a_kind_word_binds_to_a_class.sql:23-41`; `crates/utopia-store/src/type_bindings.rs:114-126, 294-326, 429-489`; `crates/utopia-server/src/api/review_routes.rs:2131-2143`.
- **Confidence**: high
- **Why it matters here**: Option 1 of Q-A is possible without a schema change for all three targets, but for a kind word the only durable uuid is the base id (the binding id can be absent before the write and can change), and for an ontology proposal a new lookup of `id` by section and key is needed.

## Assigned questions — answers

- How does the ledger name a target that has no single uuid (a kind word, an ontology proposal keyed by section and key, a run on the base), and does that need migration 0130 (map F4)? → Three options: (1) an existing uuid in `target_id` (the `ontology_proposals.id` row id looked up by section and key; the base id for a run and, durably, for a kind word) with the natural key in `target_key`; (2) migration 0130 making `target_id` nullable; (3) a derived v5 uuid. Only option 2 needs migration 0130. The evidence favours option 1: no migration, `CURRENT_SCHEMA_VERSION` stays 115, no existing test breaks, and the open-proposal identity already lives in `target_key`; option 2 breaks the `"target_id uuid NOT NULL"` assertion and at least thirteen `row.target_id == uuid` comparisons outside the edits E22 allows; option 3 needs the `uuid` crate's `v5` feature and names no row. Findings S1 to S5; sources `migrations/0128_a_token_agent_action_is_kept_in_its_own_ledger.sql:24-25`, `migrations/0129_a_token_agent_action_keeps_its_reason_its_batch_its_merge_and_its_later_state.sql:33, 56-58`, `crates/utopia-store/src/token_agent_actions.rs:51-79, 330-380, 1420-1436`, `migrations/0004_ontology.sql:60-82`, `crates/utopia-store/src/type_bindings.rs:294-326`, `crates/utopia-store/tests/a_token_keep_is_never_human_precedent.rs:343-361`, `Cargo.toml:40`.
- Where do the token and MCP reads of mappings and open ontology proposals sit: a new section name on the existing list, or their own routes opened to a token (map F11, F12)? → Three options: (1) new section names on `GET /kbs/{id}/review?queue=` for tokens; (2) the dedicated routes `GET /kbs/{id}/mappings` and `GET /kbs/{id}/ontology/proposals` moved to `SessionOrToken`, with MCP reaching them through `review_list` section names or new read tools; (3) MCP only, which does not meet the INTENT scope "Token and MCP reads". The evidence favours option 2 for the token API: no existing assertion changes, a session's answers are unchanged by construction, and it returns the fields a person sees, including the confirmed and rejected mappings E13 refers to; option 1 is one array entry for `mappings` but rewrites four tests that pin `unknown_queue`, the `thirteen` description test and ADR 0076 decision 13, and ontology proposals have no paged list, total or `id` today. The two kinds need not take the same option. Findings S6 to S8; sources `crates/utopia-server/src/api/review_ops.rs:86-125, 201-286`, `crates/utopia-server/src/api/review_routes.rs:171-174`, `crates/utopia-server/src/api/mapping_routes.rs:22-73`, `crates/utopia-server/src/api/ontology_routes.rs:568-599`, `crates/utopia-server/src/api/review_token_reads_tests.rs:405-468`, `crates/utopia-server/src/api/review_mcp_reads_tests.rs:964-1007, 1135-1158`, `crates/utopia-server/src/api/review_tools.rs:497-533`.

## Options weighed per question

### "How does the ledger name a target that has no single uuid (a kind word, an ontology proposal keyed by section and key, a run on the base), and does that need migration 0130 (map F4)?"

Three viable options; a migration is needed only for option 2. Sources: S1 to S5.

| | Option 1: existing uuid in `target_id`, natural key in `target_key` | Option 2: migration 0130, `target_id` nullable | Option 3: derived (v5) uuid |
|---|---|---|---|
| Ontology proposal | `target_id` = `ontology_proposals.id`, stable for the life of `(kb, section, key)` (S2); needs one new lookup by section and key (no reader returns `id`); `target_key` = a text of section and key; the approve arm reads section and key from the payload, as `approve_manual_merge` reads its ids | `target_id` NULL, `target_key` as in option 1 | `target_id` = hash of section and key |
| Kind word | `target_id` = the base id (durable), or the binding row id read inside the write transaction (`decide_and_apply_human_tx` takes the caller's transaction; the id can be new and is lost if the class is deleted); `target_key` = the normalized word. The operation finalizes, so its `applied` row is outside the open-proposal index | NULL plus the word in `target_key` | hash of the word |
| Run on the base | `target_id` = `kb_id`, which is what E14 says in words ("whose target is the base"); `applied`, outside the index | NULL | hash of the base and operation |
| Schema, version | none; `CURRENT_SCHEMA_VERSION` stays 115 | one file; 115 → 116; upstream number check; replay behaviour of `DROP NOT NULL` not documented (S3) | none; stays 115 |
| Structs and literals | none | `TokenAgentAction`, `NewRow`, five literals, `record_revert`, two approve arms, web interface type (S1, S3) | none; adds crate feature `v5` to `Cargo.toml:40` (S4) |
| Existing tests | none broken | the 0128 column assertion and at least thirteen `row.target_id == uuid` comparisons in seven files (S3), outside the edits E22 allows | none broken |
| What a reader gets in `target_id` | a real row id (proposal), or the base id (run, kind word) with `target_kind` telling them apart | null, honest about "no single uuid" | an id that names no row |

  The evidence favours option 1: it breaks no existing test and needs no migration, the proposal identity already lives in `target_key` (S1), E14 already words the run's target as the base, and the audit table shows the established way to carry a natural key beside an id (`alignment.kind_word_decided` writes target id `None` with the word in detail, S2). Its weak point is the kind word, where the honest uuid is the base id. Under every option the Agent History row needs new optional keys to name the target in words (S5).

## Dead ends

- PostgreSQL 16 `ALTER TABLE` page, for whether `ALTER COLUMN … DROP NOT NULL` is a no-op on an already nullable column — the page does not say; idempotency of a 0130 written that way is unverified and would have to be shown by a replay test like `replaying_migration_0128_changes_nothing`.
- docs.rs `uuid` page, for a stated determinism guarantee of `new_v5` — only "creates a UUID using a name from a namespace, based on the SHA-1 hash"; no sentence says equal inputs give equal output.
- Looking for an existing row id returned with ontology proposals or kind-word bindings — none: `StoredProposal` and `Binding` carry no `id`, so option 1 of Q-A needs a new lookup either way.
- Looking for a test that pins a token's 401 on `GET /kbs/{id}/mappings` or `GET /kbs/{id}/ontology/proposals` — none found by grep of `*_tests.rs`; test files outside `crates/utopia-server/src` were not searched for these two URLs.
- `web/src/docs/mcp.md:240, 242` mention `target_id` or `target_key` (grep hit on long lines); the lines were not read, so what the documentation promises about `target_id` being a uuid is unchecked.
- The status an opened route gives to the mismatched bodies in the shared 401 test (S11, S13) — inferred from request structs and extractor order; no server was run.
- `question_routes::adopt` and `ontology_agent::adopt` beyond the handler signature, and `scripts/check-upstream-numbers.sh`, were not re-read; the codebase map F12 and F21 stand for them.
- Conflict, recorded and not resolved: ruled table "Answer a governor decision — propose only" versus SYNTHESIS.md:73 and ADR 0076 decision 9 "`review/agent/{decision_id}` stays session-only" (S10). Also assigned to the domain and pitfalls dimensions.
