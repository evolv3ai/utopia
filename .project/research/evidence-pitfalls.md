# Evidence — pitfalls

<!-- Written by one researcher role. Consumed by the decider. -->

Dimension: pitfalls
Questions assigned: The ruled table makes "answer a governor decision" propose only for a token, while the synthesis keeps the governor's own decision route session-only. Through which token route and MCP tool does an agent propose an answer to a governor decision, given that in code that answer is a second way to merge, keep, revert or manually merge a pair as a person (map F12)? The behaviour is ruled in edge E6; the route and tool are open.; How is "the target can no longer be decided" detected per operation without matching error texts, so that approval closes a stale proposal as `superseded` (map F5, F22)?; Does a token's proposal enter through the person's route with a token branch (the nod route included) or through a separate route, given the tests that pin 401 on those routes and the charter veto on the nod (map F13, F19)?

Method: all code statements are static readings of `D:\utopia` at `d5d2356` (branch `gsd-path/M004`) with Read/Grep; no build, test, server or database command was run. Paths are relative to the repository root. "Not run" behaviour is marked in the Confidence line. Web sources were opened on 2026-11-20.

## Finding: P1 — A token keep or merge already decides a pair the governor has an open proposal on, and leaves the governor's row open and unanswerable

- **Claim**: `review_ops::keep` and `merge_pair` do not call `after_human_decision`, so `governance::answer_open` never runs for a token decision; the governor's `agent_decisions` row stays `proposed` while the review row becomes `kept`/`merged`. A person who then clicks keep or merge on that governor row reaches `agent_answer` shape `("proposed", merge|keep)`, whose first step `resolution::decide_review` selects only `status = 'pending'` and returns `NotFound`, so the answer is 404 and `settle` is never reached. No statement closes such a row: the only writers of `agent_decisions.status` are `settle`, `answer_open`, `supersede_siblings`, `settle_by_merge`. The Agent badge counts it (`status = 'proposed'`, no join on the review).
- **Source**: `crates/utopia-server/src/api/review_ops.rs:355-388, 482-506`; `crates/utopia-server/src/api/review_routes.rs:451-468`; `crates/utopia-store/src/resolution.rs:2044-2052`; `crates/utopia-store/src/governance.rs:1011-1085, 1119-1136`; `crates/utopia-store/src/review.rs:88-89`; `web/src/pages/Review.tsx:637-663` (buttons shown for every `proposed` row); tests that pin "the governor's proposal on the pair must stay open for a person": `crates/utopia-server/src/api/review_token_api_tests.rs:568-624`, `review_token_merge_tests.rs:1855-1914`. Confidence note: high that the row stays `proposed` (asserted by two tests); medium that the person's later answer is 404 (code path read, not run).
- **Confidence**: medium
- **Why it matters here**: Under "no new kind" (option 2 of Q-A) this is the standing behaviour: a token decides the pair, the governor's question is never answered, and each new token write on a governor-proposed pair adds one dead row to the Agent rail badge that E11 extends.

## Finding: P2 — The merge gate has no hold for "the governor proposed or decided otherwise"; a token can finalize against the governor today

- **Claim**: `hold_for_token_merge` is `hold_for_merge` plus `kept_by_person` (latest decided review `kept` with `decided_by IS NOT NULL AND decided_token IS NULL`) and `reverted_merge`. A governor keep has `decided_by` NULL, and an open governor proposal is not consulted at all. So a token merge of a pair the governor proposed to keep, a token keep of a pair the governor proposed to merge, and a token manual merge of a pair the governor auto-kept all finalize when the four `hold_for_merge` checks pass. None of them settles the governor's row (it stays `proposed` or `applied`), none is precedent, none starts a govern round.
- **Source**: `crates/utopia-store/src/execution_gate.rs:279-318`; `crates/utopia-store/src/token_agent_actions.rs:540-615` (no read of `agent_decisions`); ADR 0076 decision 9 (`docs/decisions/0076-…md:199-204`: "a token action starts no govern round and settles no governor proposal") and decision 14 "The precedent rule" (`:410-416`). Confidence note: high (code); the three scenarios were not executed.
- **Confidence**: high
- **Why it matters here**: Whether this is an "override of the governor by a token" is a wording question the ADR already answered in the negative: the governor's row is not answered, so the table row "answer a governor decision: propose only" holds formally. In effect the pair is decided without a person. INTENT scope-out forbids changing M003 keep/merge behaviour, so M004 cannot close this by adding a hold; it can only document it.

## Finding: P3 — Two of the three `agent_answer` shapes are already reachable as M003 proposals; the third and "accept a keep" are not

- **Claim**: (a) `(applied, revert)`: a token revert of a governor's merge lands a `merge.revert` proposal with reason `merge_by_governor`; approval runs `resolution::revert_merge` + `governance::after_revert`, which settles the governor row `reverted` with the person as `decided_by` and counts the fuse — the same effects as the `agent_answer` revert shape (audit detail differs: `agent_proposal` instead of `agent_decision`). (b) `(proposed, merge)`: a token merge that the gate holds lands a `review.merge` proposal; approval runs `decide_review` + `after_human_decision(Some("merge"))`, whose `answer_open` settles the governor row `accepted`/`overridden`. Not reachable as a proposal today: `(proposed, keep)` — a token keep finalizes, it never proposes (P1); `(applied, merge)` on a governor keep — a token manual merge finalizes when the gate passes (P2) and leaves the row `applied`; and a `(proposed, merge)` where the gate does not hold finalizes instead of proposing.
- **Source**: `crates/utopia-server/src/api/review_routes.rs:481-503` vs `:798-838`; `:452-480` vs `:655-728`; `crates/utopia-server/src/governance.rs:970-1013`; test `review_proposal_answer_tests.rs:1213-1334` (fuse counts on approval of a token-proposed revert of a governor merge).
- **Confidence**: high
- **Why it matters here**: Option 2 covers the revert shape exactly and the merge shape only when the gate happens to hold; it cannot produce "a token's proposed answer … changes neither the governor's decision row nor the pair" (E6) for keep, because keep finalizes.

## Finding: P4 — `agent_answer` is three non-atomic steps; a stale decision can be half-applied and reported as an error

- **Claim**: Each shape reads the decision once (`governance::get`), runs the pair change in its own committed transaction (`decide_review`, `revert_merge` or `merge_entities`), then calls `governance::settle`, which is guarded by `status IN ('proposed','applied')` and returns uncoded `Conflict("this decision has already been answered")`; the audit row is best effort after that. If the governor row is settled between the read and `settle` (another person's answer, or `supersede_siblings` from a decision on a sibling pair), the merge/keep/revert is committed and the call returns 409 with no audit row and no `after_human_decision`/`fuse` call. A decision whose status is no longer `proposed`/`applied` at the first read falls to the catch-all `Invalid` code `agent_answer` ("cannot keep an agent decision that is accepted", 422), which `target_gone` does not recognise. A decision id of another base is `NotFound`.
- **Source**: `crates/utopia-server/src/api/review_routes.rs:446-554`; `crates/utopia-store/src/governance.rs:920-927, 1011-1035, 1063-1085`; `crates/utopia-store/src/token_agent_actions.rs:1112-1120`. Confidence note: high (code); race not reproduced.
- **Confidence**: high
- **Why it matters here**: If approval of a governor-answer proposal runs this code as the person (option 1), staleness must be read from `agent_decisions.status` before the call; mapping the returned error would turn the 422 into a failed approval, and mapping the post-merge 409 to `superseded` would report "nothing changed" (E8) after a merge was made.

## Finding: P5 — A governor-answer proposal kind adds overlapping and contradicting open proposals on one pair, and E2's index does not prevent them

- **Claim**: The open-proposal index is `(kb_id, operation, target_key)`. A new operation (say `governor.answer`, target the decision id) can be open beside a `review.merge` proposal (target the review id), a `merge.manual` proposal (target the entity pair) and a `merge.revert` proposal (target the merge id) that all concern the same pair, from one token or several; and the same token can still finalize `review_keep` on the pair while its governor-answer proposal waits. The payload must also carry the action, because `"merge"` means "accept/override a proposal" on a `proposed` decision and "override an applied keep" on an `applied` one (`review_routes.rs:452` vs `:504`). The bulk answer applies ids in request order under one process-local mutex, so two contradicting approvals in one request resolve as "first listed wins, second must be detected stale".
- **Source**: `crates/utopia-store/src/token_agent_actions.rs:346-380` (index use), `:598, 1303-1350` (target keys); `crates/utopia-server/src/api/review_routes.rs:590, 857, 959-994`; `web/src/pages/Review.tsx:2320-2365` ("select the open ones on this page" then one Approve button, no per-kind filter, no confirmation step). Confidence note: high for the index and ordering; medium for the UI consequence (static read of the component, not clicked).
- **Confidence**: medium
- **Why it matters here**: Option 1 needs a stale rule that sees through to the pair: after an approved `review.merge` the governor row is `accepted` (via `answer_open`), so the governor-answer proposal must close `superseded` from the status read, not from the 422 in P4.

## Finding: P6 — Precedent, fuse and govern-round effects of an approved governor answer are the person's, by construction, only if approval writes no `token_id`

- **Claim**: Precedent reads exclude audit rows whose detail has a `token_id` key (`NOT_BY_TOKEN`) and review rows with `decided_token`. `agent_answer` writes `decided_by = person`, no `decided_token`, and audit detail `{left,right,agent_decision,agent_action,why}`; an approval that reuses it and adds only `agent_proposal` counts as human precedent, queues a govern round (`after_human_decision` when `kb.governance`), supersedes sibling governor proposals, and on the revert shape counts toward the two-reverts-in-seven-days fuse. The M003 approval arms follow the same rule on purpose ("detail 里不带 token_id").
- **Source**: `crates/utopia-store/src/governance.rs:81-136, 602-621, 1087-1102`; `crates/utopia-server/src/api/review_routes.rs:563-567, 896-897`; `crates/utopia-server/src/governance.rs:982-1013`; ADR 0025 decision 1 (`docs/decisions/0025-…md:19`: "A proposal a person accepted counts").
- **Confidence**: high
- **Why it matters here**: E6 and E7 rule exactly this; the failure mode is the inverse — an approval arm that copies the token's `rationale` into `why` or adds `token_id`/`proposed_by_token` under the key `token_id` would silently drop the row from precedent, or make an agent's sentence the "why" a later governor round quotes as a person's. M003 passes `None` for the rationale on approval (`review_routes.rs:699-707`).

## Finding: P8 — `target_gone` treats every `NotFound` as stale and knows two merge strings; extended as it is, it would mislabel four cases

- **Claim**: `target_gone` returns true for `AppError::NotFound`, and for `Conflict` only when the text equals `resolution::ALREADY_MERGED` or `"Merge already reverted"`. `gone_or` passes every other error through so that "the governor is deciding this pair" keeps the proposal open. Applied unchanged to the M004 kinds it would: close `superseded` a violation proposal whose fact was just retracted by this very approval (P7, violation row); leave a governor-answer proposal open with a 422 forever (only decline closes it); treat `alignment_busy` correctly as "not gone" only because it is a `CodedConflict`; and never see the stale cases that return success (close fact `Ok(None)`, ontology reject, errata lost race). The M003 arms do not rely on it alone: each reads the target's state first (`rr.status`, `merged_into`, `reverted_at`) and compares the payload's entity ids with the current row before calling the person's function.
- **Source**: `crates/utopia-store/src/token_agent_actions.rs:280-291, 1109-1126`; `crates/utopia-server/src/api/review_routes.rs:618-626, 663-698, 754-768, 804-822`.
- **Confidence**: high
- **Why it matters here**: The M003 pattern is already "typed pre-read, then the person's function, with error mapping as the backstop"; the question for M004 is how much of the backstop each kind can safely keep.

## Finding: P9 — Check-then-act is racy for every kind, and the lock that serialises answers does not cover the person's own routes

- **Claim**: `ANSWERING` is a process-local `tokio::sync::Mutex` taken only in `answer_proposal`; the session handlers of every section, the governor job, the errata agent, the aligner and the timer-driven inference do not take it. A pre-check read in an approval arm can therefore be invalidated before the person's function runs. Where the person's function has its own guard the race is closed by it (conflict: row lock and re-read; reject fact, defect, violation `decide`: guarded UPDATE; adopt: `FOR UPDATE`; governor `settle`: guarded, but after the pair change). Where it has none the race stays open: errata approve (double apply), nod confirm/reject (double audit row, confirm+reject both "succeed"), close fact (`valid_to` not re-checked), confirm fact and the two alignment decisions (no decided state to violate). The ADR already lists "A person's approval is not one transaction with its merge" as a known limit and says answers "are serialised within one server process only".
- **Source**: `crates/utopia-server/src/api/review_routes.rs:585-590, 857`; ADR 0076 `:460-474`; guards as cited in P7. Outside source: CWE-367 "Time-of-check Time-of-use (TOCTOU) Race Condition" — "The product checks the state of a resource before using that resource, but the resource's state can change between the check and the use in a way that invalidates the results of the check"; mitigations "Ensure that locking occurs before the check, as opposed to afterwards", "Recheck the resource after the use call to verify that the action was taken appropriately" (https://cwe.mitre.org/data/definitions/367.html). Confidence note: high (code and source); no race was reproduced.
- **Confidence**: high
- **Why it matters here**: A pre-check alone gives a correct `superseded` in the common case and a wrong `approved` in the rare one; only a guard inside the write (existing, or a status-guarded variant) makes E8 exact, and adding a guard to a person's function touches code INTENT says must not change for a signed-in person.

## Finding: P10 — A proposal can go stale by content while its target id stays decidable

- **Claim**: Three targets can change under the same id or key while a proposal waits: a conflict ("a rewrite may have carried this conflict to different rows" — the function re-reads `old_fact_id/new_fact_id`); an open ontology proposal, which a later agent round rewrites in place `WHERE status = 'open'` under the same `(section, key)`; and a phrase binding, which the aligner may re-decide until a person does. Approval by id/key then applies the stored action to content the token never saw. M003 handles the analogous case for queue merges by storing the two entity ids in the payload and closing the proposal as gone when the review row no longer names them.
- **Source**: `crates/utopia-store/src/temporal/conflicts.rs:81-104`; ADR 0076 "Ontology adoption finding" (`:487-490`: "a refresh rewrites it only `WHERE status = 'open'`"); `crates/utopia-store/src/phrase_bindings.rs:441-453`; `crates/utopia-server/src/api/review_routes.rs:692-698`. Confidence note: medium (the refresh and re-decision paths were read through the ADR and the upsert, not traced end to end).
- **Confidence**: medium
- **Why it matters here**: E8 names only "gone or decided"; whether content drift is `superseded` is not ruled, and the M003 precedent treats it as such for merges.

## Finding: P11 — Body validity can change between propose and approve, giving a third outcome that is neither approved nor superseded

- **Claim**: E4 validates the body when proposed, but several refusals depend on state that can move: `interval_inverted` (the fact's start was retimed), `close_at_required` (the new fact lost its start), `not_open` on violation `fact_closed` (the fact was closed), `fact_required` (the violation's fact set), `unknown_property`/`unknown_class` (the ontology changed), `not_a_merge`. At approval these come back as `AppError::Invalid` (422). In the M003 shell every error other than "gone" leaves the proposal open and is returned to the person (single) or as that item's `code` (bulk, `outcome_error`).
- **Source**: `crates/utopia-store/src/temporal.rs:902-909`; `temporal/conflicts.rs:126-153`; `crates/utopia-server/src/api/review_routes.rs:1562-1616, 1983-2037, 940-954, 865-895`. Confidence note: high that the codes are state-dependent; medium on how often it occurs.
- **Confidence**: medium
- **Why it matters here**: Such a proposal can never be approved and is not stale by E8's wording; unless a rule closes it, it stays open until declined, keeps the item's card chip and the rail badge, and blocks a corrected proposal for the same operation and target (`already_proposed`, E2).

## Finding: P12 — The propose-time check (E3) cannot be built from the person's errors, because they collapse "unknown" and "decided"

- **Claim**: E3 needs three answers at propose time — not found, `already_decided`, proposable — and E1 forbids running the person's function to find out. For conflict, violation, defect, errata, ontology adopt and reject/close fact the person's function returns the same `NotFound` (or `false`, or `{ok:true}`) for an unknown id, an id of another base and a decided target. Each of those targets has a status column that distinguishes the three with one `SELECT … WHERE kb_id = $1 AND id = $2` (`fact_conflicts.status`, `axiom_violations.status`, `ontology_defects.status`, `errata_actions.status`, `ontology_proposals.status`, `agent_decisions.status`, `facts.invalidated_at`/`valid_to`). Pending facts, phrase bindings and implication rules have only row presence, which matches E17 ("unknown or already nodded is not found") and E8 ("no decided state").
- **Source**: P7 sources; `.project/intent/INTENT.md:54, 68`.
- **Confidence**: high
- **Why it matters here**: The same typed status read serves both ends: at propose time it yields not-found / `already_decided`; at approval it yields `superseded` before the person's function is called.

## Finding: P13 — In a shared handler the only thing between a token and the session code is one early `return`; nothing in the type system separates the branches

- **Claim**: `SessionOrToken` yields `{user, pat: Option<Authenticated>}`; a credential starting with the token prefix is authenticated as a token, anything else is decoded as a session JWT, so one request cannot be both. Each M003 handler then does `let user = caller.user; if let Some(token) = caller.pat { …; return … }` and falls through to the unchanged session body with `user` bound to the owner. If a token branch misses a `return` on any path (for example an unmatched action arm), execution continues into the session body as the token's owner — an Editor — and finalizes. `decide` shows the care needed: its unmatched-action arm authorizes and returns `not_open` explicitly. The existing kind-word handler shows the opposite shape: it has no branch at all and a token runs the session code. No test asserts the property structurally; it is shown per operation by behaviour (a token merge of a gate-held pair lands a proposal where the session path would merge; a token keep queues no govern job where a session keep queues one).
- **Source**: `crates/utopia-server/src/auth.rs:191-217`; `crates/utopia-server/src/api/review_routes.rs:353-375, 1015-1035, 1270-1301, 2091-2100`; tests `review_token_merge_tests.rs:1855-1914`, `review_token_api_tests.rs:568-634`.
- **Confidence**: high
- **Why it matters here**: For most operations a slip finalizes something the table rules propose only (N9). For the nod the same slip is a breach of the charter veto (N4), and the session and token requests would be byte-identical (`{"action":"confirm"}` on the same URL).

## Finding: P14 — The body extractor runs before any token check, so a shared handler answers a malformed body before `token_read_only`

- **Claim**: axum runs extractors left to right and does not call the handler when one rejects. Every person's write handler takes `Json<…>` as its last parameter, so once `AuthUser` becomes `SessionOrToken` a read-scope token (or a below-editor owner) sending a body that fails to deserialize gets axum's own 4xx rejection, with no stable code, before `authorize_write` can answer `token_read_only`. M003 met this on the revert route and took the body as raw `Bytes` so the token branch could answer scope first ("先说「你写不了」，再说「你写错了」"). The existing 401 test sends bodies that do not deserialize on five routes (`{"action":"dismiss"}` to violations and defects, `{"action":"approve"}` to errata and rules, `{"action":"keep_both"}` to conflicts), which pass today only because the extractor rejects first.
- **Source**: https://docs.rs/axum/0.8.4/axum/extract/index.html ("Extractors always run in the order of the function parameters that is from left to right"; "If an extractor fails it will return a response with the error and your handler will not be called"); `crates/utopia-server/src/api/review_routes.rs:1268-1295, 1528-1533, 1734-1739, 2155-2160`; `review_token_reads_tests.rs:1097-1142`. Confidence note: high for the mechanism; the resulting status per route was not run.
- **Confidence**: high
- **Why it matters here**: E19 and E4 both rule the refusal a token gets; in a shared handler the order "scope, role, then body" holds only if the body is parsed inside the token branch. A separate token route has the same extractor order unless it also takes raw bytes.

## Finding: P15 — The nod route's 401 is the only standing test that a token cannot nod; a token branch replaces it with a weaker assertion in the one test eleven tasks must edit

### Q-A — governor answer

Scope: Failure modes only (route and tool names are the domain dimension's part). Two shapes were examined; sources are findings P1–P6.

Option 1 — a new proposal kind whose approval runs the person's governor answer:

- Stale decision: staleness must be read from `agent_decisions.status` (and `action`, `merge_id`) before the person's code runs. The person's code answers a decided decision with 422 `agent_answer`, an already-token-decided pair with `NotFound`, and a decision settled mid-way with a 409 after the pair change committed (P4). Error mapping gives a stuck proposal in the first case and a false "nothing changed" in the third.
- Overlap: the proposal can be open beside `review.merge`, `merge.manual` and `merge.revert` proposals on the same pair, and beside the same token's finalizing keep (P5). The stale rule has to follow the pair, because approving any of the others settles the governor row through `answer_open` or `settle_by_merge`.
- Payload: the action must be stored and bound to the decision's status at propose time; `merge` means two different things on a `proposed` and an `applied` decision (P5).
- Precedent, fuse, govern round: as ruled in E6/E7 they are the person's on approval; the trap is an approval arm that carries the token's rationale as the person's `why`, or writes a `token_id` key, which changes what the governor later reads (P6).
- A running govern round answers an uncoded 409 that is "retry", not stale; M003 already keeps the proposal open for it (ADR 0076 decision 14).
- Non-atomicity: approval is read, pair change, settle, audit, close-proposal — one more non-transactional sequence added to the known limit list (P4, P9).

Option 2 — no new kind; the agent uses merge, keep and revert on the pair and the governor route stays session-only:

- What holds: the governor's row is never answered by a token (ADR decision 9, tests in P1), a revert of a governor merge is already a proposal whose approval settles the row and counts the fuse (P3a), and a gate-held merge is already a proposal whose approval settles the row (P3b).
- What does not: a token keep on a governor-proposed pair, a token merge the gate passes, and a token manual merge of a governor-kept pair finalize today (P1, P2). The table row "propose only" then holds for the governor's row and not for the pair. ADR 0076 decision 9 and its 2026-11-19 revision rule this as intended ("settles no governor proposal"; "No token action … settles a pair as decided by people"), and INTENT scope-out forbids changing it.
- Side effect that grows: every such token decision leaves a `proposed` governor row that a person can no longer answer (404) and that the Agent badge counts (P1).
- Coverage gap: "accept the governor's keep proposal" has no proposal form, because keep finalizes (P3).
- Conflict with INTENT, recorded and not resolved: INTENT scope-in names "a proposed answer to a governor decision" as a propose-only operation that lands in the proposal store, and E6 rules the behaviour of "a token's proposed answer to a governor decision". Option 2 lands no such proposal.

Which option the evidence favours: option 1, on the condition that its approval arm decides stale from a typed read of the decision and the review row (P4, P5, P12). Reasons: it is the only shape that satisfies INTENT scope-in and E6 as written, and it is the only one in which keep on a governor-proposed pair can be proposed rather than finalized. Option 2 is cheaper and adds no overlap, but leaves the row's ruling true only in name and is in tension with the approved intent. Neither option removes P1/P2, which are M003 behaviour; the ADR's final text should state them (N11).

### Q-B — detecting a stale target

Scope: No single mechanism is safe for all kinds; the per-operation table is finding P7, the current string matcher is P8, the race analysis P9, content drift P10, state-dependent body refusals P11, propose-time reuse P12.

Options:

1. **Typed pre-check per kind, before the person's function** (one status read scoped by base: `Open`, `Decided`, `Missing`; for conflict, queue-style kinds and ontology proposals optionally a payload comparison, P10). Covers every kind that has a status column, is the only way to see the "success that did nothing" cases (close fact, ontology reject) and the governor's 422, and is what the three M003 arms already do. It is check-then-act (P9): correct alone only where the person's function has its own guard behind it. The same read serves E3 at propose time (P12).
2. **Mapping typed errors per kind** (`NotFound` → stale for kinds where the function is a single guarded statement or one transaction: reject fact, defect, conflict, ontology adopt; never for uncoded `Conflict`). Needs no new read and is exact for those four, because the guard and the write are one unit. Unsafe as the sole rule for violation `fact_retracted`, errata approve, nod confirm and the governor answer, where an error can follow a committed step (P7), and blind to the success-without-effect cases. Distinguishing conflict's "changed before it could be decided" (stale) from the governor's "deciding this pair right now" (retry) without text needs a coded variant, which is a change to a store function a person also calls (the code on the person's 409 would gain a `code` field).
3. **Status-guarded variant** (a new store entry per kind that takes the row lock, checks status and writes in one transaction, returning a typed `Stale`). Exact under concurrency and across processes. Cost: a second writer per kind beside the person's function for the non-transactional kinds (violation, errata, nod, governor answer), which E7 rules against ("approval runs the person's own store function") unless the variant wraps the person's function inside the caller's transaction — possible only where that function accepts a connection (`close_superseded`, `retract`, `decide_on`, `adopt_on` do; `pending::confirm`, `errata::decide_held`, `reasoning::decide`, `decide_review` take the pool).

Per kind, what the evidence supports:

- Confirm fact: stale = fact missing or invalidated (`facts.invalidated_at`); the function's own guard gives `NotFound` atomically, so option 1 or 2 is exact. No decided state (E8).
- Reject fact: same column; option 2 is exact (guarded UPDATE in one transaction); option 1 adds E3's `already_decided`.
- Close fact: needs option 1 (`invalidated_at IS NULL AND valid_to IS NULL`, scoped by base — the store function takes no base id) and must treat the store's `Ok(None)` as stale; the handler's ignoring of `None` must not be copied (P7).
- Resolve conflict: option 2 on `NotFound` is exact; the uncoded "changed" 409 and a `NotFound` from the inner close are stale by meaning but only a pre-read (`status = 'open'`, both facts live, optionally the fact ids stored in the payload) identifies them without text.
- Violation: option 1 on `axiom_violations.status`, plus, for `fact_retracted`/`fact_closed`, the body's fact still live/open; a `NotFound` after the call cannot be read as "nothing changed" (P7). `not_open` and `fact_required` at approval are P11 cases.
- Defect: option 2 exact; option 1 for E3.
- Errata: option 1 on `status = 'held'`; `Ok(false)` is already a typed stale signal. The double-apply race under two processes remains (P9) unless option 3.
- Alignment phrase and rule: stale = row missing only (`signature_of` / `get` → `None`), per E8; refusals such as `unknown_property` at approval are P11.
- Ontology reject: option 1 is required (the function returns nothing); read `status = 'open'` by `(section, key)`. Adopt: option 2 exact (`FOR UPDATE … status='open'` → `NotFound`); `alignment_busy` is retry, not stale. Content refresh under the same key is P10.
- Nod: stale = pending row missing (`pending::get` → `NotFound` before any write); errors after the first insert are failures, not stale (P18).
- Governor answer: option 1 on `agent_decisions.status ∈ {proposed, applied}` matching the stored action's shape, and for the `proposed` shapes the review row still `pending`; see Q-A.

Which option the evidence favours: option 1 as the rule for every kind, with option 2 kept as the backstop only for the kinds whose person function is one guarded statement or one transaction (confirm, reject, defect, conflict, adopt), and the remaining cross-process races recorded as known limits beside the two the ADR already lists. Option 3 is the only exact one for errata, nod and the governor answer, at the price of a second writer or a change to a function a person calls. Unruled points the decider or the owner must settle: whether content drift closes a proposal as `superseded` (P10); what closes a proposal whose body is no longer valid (P11); whether contradicting open proposals on one target need an ordering rule (P17).

Propose-time (E3) reuse: the same status read answers `Missing` → not found, `Decided` → `already_decided`, `Open` → land the proposal; kinds with row presence only (pending fact, phrase, rule) have just the first and third answers, which is what E17 and E8 rule. A status read before `land_proposal` is itself check-then-act; a target decided in between yields a proposal that is stale at birth and is closed at approval by the same read.

### Q-C — entry route and the nod

Scope: Safety failure modes only (the route shape itself is shared with the stack dimension). Sources: P13–P19.

Shared handler with a token branch:

- The guard is one early `return` per handler; a path that falls through runs the session body as the owner and finalizes (P13). For the nod that is a veto breach by a request identical to a person's.
- The body is parsed before scope and role unless the handler takes raw bytes, so `token_read_only` (E19) and the person's body codes (E4) come out in the wrong order (P14).
- The 401 assertions become "proposal returned"; the nod veto is then tested only by row equality (P15).
- Advantage on safety: one URL per operation means no second surface to keep closed, and it is what the synthesis and ADR decision 1 settled.

Separate route for the token's proposal:

- The person's handler keeps `AuthUser`; no code path from a token to `pending::confirm`/`reject` exists except through the session-only answer route, and the existing 401 assertions stand unchanged as the regression test (P15).
- Costs: a second route per operation that must be kept closed to sessions or defined for them, documentation of two URLs, and a departure from "no second route tree" that needs a dated ADR revision. The extractor-order point (P14) applies equally.
- A mixed shape is possible and not contradicted by any source: shared handlers for the operations where a slip breaks a ruling (N9), a separate route for the nod where a slip breaks the charter veto (N4).

Nod-specific risks that hold under either entry:

- Agent vouching for an agent: the server can know that the proposing token is the remembering token (`pending_facts.proposed_token`), but exposes only the name; the nod card shows the rememberer in fine secondary text and has no slot for a proposed answer; the bulk answer in Agent History shows neither sentence nor rememberer (P16).
- Contradicting confirm and reject proposals on one pending fact are legal (E2) and unlimited (E5); a mixed bulk approval applies the first listed (P17).
- A failed approval of a confirm can leave a live fact with no audit row and an open proposal, and a decline afterwards does not remove the fact (P18).
- Bulk approval of up to 500 proposed nods has no counterpart on the nod card; the product's own measurement shows blindly accepted proposals becoming wrong precedent, and outside sources report approval fatigue without giving a safe volume (P19).

Which option the evidence favours: for the eleven non-nod operations the evidence does not separate the two shapes on safety once the token branch parses the body itself and returns on every path; the settled synthesis decision (shared handler) stands unchallenged. For the nod, the evidence favours keeping the person's route session-only and giving the token's proposal a different entry, because it is the one operation where a branch slip crosses a charter veto and where an unchanged 401 test is available as the guard. This conflicts with the letter of ADR decision 1 and is left to decide. Independently of the entry, the evidence supports excluding or separately confirming pending-fact proposals in the bulk answer, and showing sentence, rememberer and proposer on the row a person approves from; whether that is in scope is the owner's ruling (N5 covers the nod card only).
