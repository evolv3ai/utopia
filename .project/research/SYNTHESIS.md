## Settled

- Token identity — a personal token acts as its owner, scope only narrows, every call re-checks scope; no base-level machine token or service account (program SYNTHESIS.md Settled, Token identity; ADR 0014 decisions 1, 2, 5)
- Read surface — tokens read the thirteen sections through the three handlers the Review tab already uses: `GET /kbs/{id}/review?queue=` for the eleven queue sections (`pending`, `duplicates`, `conflicts`, `unconfirmed`, `lowconf`, `violations`, `defects`, `alignment`, `errata`, `agent`, `merges`), `GET /kbs/{id}/review/summary` for Overview and `GET /kbs/{id}/review/history` for Decisions; no new list route per section. - Token access — handlers change extractor from `AuthUser` to `SessionOrToken` in place; reads pass the reader check (owner at least Viewer, base inside `kb_ids`, else 404); a dead token gets 401; a session caller's branch runs today's code (program SYNTHESIS.md Decisions, Token access to Review routes)

## For the planner

- **Wave-1 blockers**: the total. It changes the list response shape the web app reads, and three sections' counts disagree with their lists today (Alignment rules, Agent History rows, Low confidence derived facts); the per-section total and the Alignment tie-break must be proven against seeded data and the unchanged session tests before the token branches build on them. The seeding helper that puts at least one item in every one of the thirteen sections is needed by every later test and is the expensive part (errata, alignment rules, derived contradictions).
- **Walking skeleton**: one non-Duplicates queue section end to end — a read-scope token of a Viewer lists it over the token API through `review_ops::list` and over MCP `review_list`, gets the session list's items, order and `total`, and reads one item through `review_item` with `section` and `id` — then the remaining sections, Decisions (`history`), the two proof reads, refusals, and documentation.
- **Pitfalls → tasks**:
  - The eleven-queue `match` lives only in the session branch of `review_routes::list`; `review_ops::list` duplicates the clamp and shape for `duplicates` → the read task serves every queue from one place without changing what the session branch returns.
  - Two M001 tests (`a_token_asking_for_another_section_is_refused_with_unknown_queue`, `review_list_refuses_another_section_with_unknown_queue`), the MCP tool descriptions and `web/src/docs/mcp.md:208` assert today's refusal → they change with the behaviour, and the refusal stays for a truly unknown section and for `mappings`.
  - `history`, `derived_proof` and `blocked_proof` take `AuthUser` → they move to `SessionOrToken` with the reader check; their session branch is unchanged.
  - `blocked_proof` returns steps only for `derived_contradiction`; `proof` takes a derived-fact id → `review_item` for an Axioms item follows ruling E8.
  - `review_item` means a duplicate pair today → it gains `section`; an Alignment kind word is identified by its word, an Agent History row by its row id.
  - Server crate has no `lib.rs` and tests live in `src/` → token tests are sibling `*_tests.rs` files in `crates/utopia-server/src/api/`; tasks that both edit `review_routes.rs`, `review_ops.rs`, `review_tools.rs` or `mcp.rs` cannot run concurrently.
  - Backend build reads `web/src/docs/` → a documentation task that touches `web/src/docs/mcp.md` rebuilds the server in its Verify.
  - The web app reads the list response → the task that adds `total` updates `web/src/api.ts` types only as far as needed and proves the web tests and build still pass (install first: `pnpm install --frozen-lockfile`).
  - Every Verify runs in a fresh sidecar with nothing installed, on its own database, with its own empty `CARGO_TARGET_DIR` outside the worktree and PostgreSQL 16 client tools on PATH (`.project/LESSONS.md`).
  - `cargo fmt --all --check` currently fails on two spots in `crates/utopia-server/src/api/review_attribution_tests.rs` (docs audit, M002 inspect) → a task that touches the server crate leaves formatting clean in the files it owns.
