### Token access to Review routes: extractor, checks, error codes

- **Decision**: The existing Review handlers change extractor from `AuthUser` to `SessionOrToken` in place (same URLs, no parallel route tree). Reads call `require_reader_kb` (owner at least Viewer, token reaches the base, 404 when `kb_ids` exclude it). Writes follow the order already used by `decide_alignment_kind_word`: `require_write(Some(kb_id))` first, then `require_kb(.., Role::Editor)`. Stable codes: existing `token_read_only` and `token_kb_out_of_scope`; new coded 403 `token_owner_below_editor` for a token whose owner is below Editor (today a plain 403); new coded conflicts `already_decided` (lost race or repeated call) and `already_proposed` (an open proposal exists for the same target); new coded 429 `agent_rate_limited`. A session caller's requests and responses are unchanged.
- **Runner-up**: A separate token-only route tree under a new prefix with its own extractor. It lost because the one-helper token pattern already exists in this file and in eleven read routes, and success criterion 1 (the same items a signed-in editor sees) is safest when both callers run the same handler.
- **Evidence**: evidence-stack.md § At HEAD, eleven read routes plus three document reads and the base list accept a personal token through one extractor; evidence-stack.md § Token refusals on those routes have fixed statuses, and only the write refusals carry a stable code; evidence-stack.md § Review routes are session-only at HEAD, so a personal token gets 401 there; evidence-pitfalls.md § A person, the governor and a token-agent can race on one item with partial guards
- **Confidence**: high

### Token-agent write path and the ADR 0027 execution gate

- **Decision**: Token-agent writes do not reuse the session handlers' bodies. Each write handler branches on the caller: a session caller runs today's code unchanged; a token caller is passed to one shared server-side policy function that lives with the `execution_gate` module (ADR 0027 decision 3 names an agent's calls as that module's next caller). The policy holds a compiled-in per-operation table (the owner's ruling) and returns one of three outcomes: `applied` (the same store function the person's path calls), `held` or `proposed` (a proposal row, no graph change). Every token-agent merge, single, manual or batch member, calls `execution_gate::hold_for_merge` before `merge_entities`; a hold becomes a proposal carrying the gate's reason and is never an error and never a merge. The gate also holds a merge of a pair that a person kept or that has a reverted merge. The table is not a per-base setting.
- **Runner-up**: Opening the existing handlers to tokens as they stand. It lost because the person's merge path calls no gate, so an external agent would hold a wider merge power than the product's own governor, up to 500 merges per request, which is the straight-through write the charter vetoes. A per-base configurable table also lost: ADR 0014 decision 6 keeps base settings session-only and no evidence asks for the extra surface.
- **Evidence**: evidence-domain.md § ADR 0027 names an agent's calls as this gate's next caller; evidence-domain.md § The person's merge path is not gated; only the two machine deciders call the gate; evidence-pitfalls.md § The person's Review write paths never ask the ADR 0027 merge gate; evidence-capability-map.md § A human merge path has no execution gate; the two built-in agents both stop at it; evidence-similar.md § MDM products split merge by rule class: automatic rules finalize, the rest queue for a steward; evidence-similar.md § Tamr keeps model suggestions on verified records as suggestions
- **Confidence**: high

### MCP tools over the same implementation

- **Decision**: Each Review operation is one server function that takes the resolved caller (owner id, token id, base id). The REST token branch and the MCP tool both call it, so there is one implementation of authorization, policy, gate, ledger and audit. MCP gains two read tools, `review_list` (a `section` parameter covering the thirteen sections, the existing 1 to 200 page clamp) and `review_item` (one item's evidence), and one write tool per operation family rather than one omnibus write tool. Exposure follows the `remember` rule: read tools for any token that reaches the base with an owner at least Viewer; write tools listed and callable only with scope `write` and an owner at least Editor. A refused write tool call returns a tool error whose structured content carries the same stable code as REST. `ToolAnnotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`) are set as hints only. Elicitation is not used as the nod.
- **Runner-up**: Implementing the MCP tools separately in `tools.rs` beside `remember`, or having them call the REST routes over HTTP. It lost because two implementations drift and success criteria 1 and 3 require the same result over both surfaces. Thirteen list tools, one per section, also lost: the per-section dispatch already exists as one `match queue`.
- **Evidence**: evidence-capability-map.md § Existing MCP surface is eleven read tools and `remember`; a refused tool call leaves no audit row and no stable code; evidence-similar.md § The MCP specification puts confirmation on the client, as SHOULD, and tool annotations are hints; evidence-similar.md § MCP elicitation is optional per client, so it cannot be the nod; evidence-domain.md § MCP's own "confused deputy" guidance is about OAuth proxying, not about content read through tools; evidence-pitfalls.md § The MCP specification puts access control and rate limiting on the server and treats the human check as a client SHOULD
- **Confidence**: medium

### Read surface

- **Decision**: Tokens read the thirteen sections through the three handlers the Review tab already uses, not through thirteen routes: `GET /kbs/{id}/review?queue=` for the eleven queue sections (Awaiting your nod, Duplicates, Conflicts, Unconfirmed, Low confidence, Axioms, Ontology, Alignment, Errata, Agent History, Merges), `GET /kbs/{id}/review/summary` for Overview and `GET /kbs/{id}/review/history` for Decisions. No section needs a new list route. Item evidence is the list item's own fields plus per-item reads: the already token-open `facts/{fact_id}/evidence` and `entities/{entity_id}`, and the two proof routes `violations/{violation_id}/proof` and `derived/{derived_id}/proof`, which move to `SessionOrToken` at Viewer. Three reads need new content rather than new routes: the `agent` queue also returns token-agent ledger rows, each queue item carries its open token-agent proposal when one exists, and every list response carries the true total of the listed section so a token client does not page by the Alignment badge count that omits implication rules.
- **Runner-up**: One dedicated token route per section. It lost because the tab makes three list requests, eleven sections already share one dispatch, and separate routes would have to be kept equal to the tab by hand.
- **Evidence**: evidence-capability-map.md § Only two of the thirteen sections have their own read route; eleven share `GET /kbs/{id}/review`; evidence-capability-map.md § The Review tab reads item evidence from the list item itself; it calls no per-item evidence route; evidence-capability-map.md § The Alignment badge count and the Alignment list disagree on implication rules; evidence-stack.md § At HEAD, eleven read routes plus three document reads and the base list accept a personal token through one extractor
- **Confidence**: high

### Attribution of record

- **Decision**: An agent action is recorded as owner plus token. `audit_events.actor_id` stays the owner (ADR 0014). Every token Review write adds `detail.token_id` and a `detail.token_name` snapshot taken at insert time, because `audit_events` is append-only and a detail snapshot is the existing convention. The agent's name is the personal token's name, shown as "owner via token name", the wording the Awaiting-your-nod card already uses for `remember`. The only self-reported client label used is the HTTP `User-Agent` already stored on every audit row; it is returned to readers marked as declared and is never read for authorization. MCP `clientInfo` is not parsed.
- **Runner-up**: MCP `clientInfo` or a declared agent-name field as the agent's name. It lost because the server is stateless on revision 2025-06-18 and cannot tie a `tools/call` to an `initialize`, the field is optional and unverified in every revision, and the REST token API has no equivalent.
- **Evidence**: evidence-capability-map.md § The server's only durable name for a calling agent is the personal token's `name`; MCP `clientInfo` is never read; evidence-capability-map.md § The product already shows "owner via token name" for `remember`, and nowhere else; evidence-capability-map.md § MCP `clientInfo` is self-reported, and a stateless server on the implemented revision sees it only on `initialize`; evidence-capability-map.md § The HTTP `User-Agent` of every token call is already stored on the audit row but is not returned to any reader; evidence-similar.md § GitHub attributes an agent's action to both the person and the app, and records the token type; evidence-similar.md § Wikidata and Wikipedia attribute a bot to a named account and hold the operator responsible for repair
- **Confidence**: high

### Agent History and Activity

- **Decision**: A new table `token_agent_actions` is the ledger of every token-agent Review action: base, operation, target kind and id, owner id, token id, token name snapshot, outcome (`applied`, `held`, `proposed`), later state (`approved`, `declined`, `superseded`, `undone`), gate reason, batch id, request payload, undo reference such as `merge_id`, answering person and timestamps. Agent History (`queue=agent`) returns the governor's `agent_decisions` rows unchanged plus these rows, told apart by a `source` field. Activity keeps its Admin-only session route; `AuditEventView` gains optional `token_id`, `token_name` and declared client, and the web app renders token rows as "owner via token name" with labels for the action strings it shows raw today. The Decisions section keeps its four action families, so a signed-in person's view is unchanged.
- **Runner-up**: Widening `agent_decisions` with actor and token columns and new target kinds, as ADR 0043 planned. It lost because that migration was withdrawn with PR #699, the table's constraints admit only duplicate-pair merge and keep, and the governor's precedent and fuse queries read it, so every one of them would need a token exclusion.
- **Evidence**: evidence-capability-map.md § Agent History is the governor's own table and cannot hold a token agent's action without a schema change; evidence-capability-map.md § Activity labels governor and adjudicator rows identically, and mislabels the errata agent's run row; evidence-capability-map.md § Decisions shows only four action families, so most Review writes never appear there; evidence-domain.md § ADR 0043's conflict and fact governance is accepted but not built; automatic application is explicitly waiting on a measurement
- **Confidence**: medium

### Governor precedent and the governance fuse

- **Decision**: Token-agent decisions are never human precedent. The governor's precedent queries and `settled_by_people` exclude audit rows whose detail carries a token id and review rows marked by a new nullable `resolution_reviews.decided_token` column; `after_human_decision` is not called for a token decision, so a token action starts no govern round and settles no governor proposal. The governor's own decision route, `review/agent/{decision_id}`, stays session-only. A token never finalizes a revert of a merge made by a person or by the governor, so a token cannot trip the governance fuse; such a revert is a proposal, and when a person approves it the fuse counts it as today. Token agents get their own breaker computed from the ledger with the governor's constants: two reverts by a person of one token's finalized merges on a base within seven days make that token propose-only on that base for the rest of the window. Revoking the token remains the kill switch.
- **Runner-up**: Recording token actions with a null actor, as the governor's own rows are, so that today's queries skip them unchanged. It lost because it breaks ADR 0014 decision 1 and success criterion 6 (the owner must be named) and Activity would label the row "AI adjudicator".
- **Evidence**: evidence-domain.md § An action taken with a token is recorded as the person's and would be read as human precedent; evidence-pitfalls.md § Token-agent decisions would be read by the governor as human precedent; evidence-capability-map.md § A token agent's decisions would be stored as human precedent and would steer the governor; evidence-domain.md § A token-made revert would count toward the governance fuse; evidence-pitfalls.md § The governor's fuse does not count token-agent merges, and a token-agent could trip it; evidence-pitfalls.md § `review/agent/{decision_id}` answers the governor through the person's path, in three shapes; evidence-similar.md § A fully autonomous bot that finalizes is allowed where its action is itself an undo and its error rate is capped
- **Confidence**: medium

### Proposal store

- **Decision**: A propose-only or held operation waits as a `token_agent_actions` row with outcome `proposed` or `held`; the ledger is the general proposal store. A partial unique index allows one open proposal per base, operation and target; a repeat returns the existing proposal with `already_proposed`. The row holds the full request payload and changes no fact, entity, review row, retrieval or reasoning. A person answers it in the Agent History section, where governor proposals are already answered, and the item's card in its own section shows the open proposal. The answer route takes `AuthUser` only: no token may approve or decline a proposal. Approval runs the existing session store function with the person as actor and `detail.agent_proposal` naming the proposal; if the target can no longer be decided the proposal closes as `superseded`. A person may answer many proposals in one session request, capped at the existing 500. `pending_facts` and `errata_actions` keep their own stores and are not migrated.
- **Runner-up**: Reusing the three per-kind stores (`pending_facts`, `agent_decisions`, `errata_actions`) and adding one more per operation. It lost because confirm, reject, close, conflict, revert, alignment, violation and defect proposals have nowhere to land today and each new store would need its own uniqueness rule, queue and answer route.
- **Evidence**: evidence-pitfalls.md § There is no general proposal store; the propose path exists for three item kinds only; evidence-similar.md § Wikipedia's pending-changes model holds an edit out of the reader's view until a reviewer accepts; evidence-similar.md § GitHub's model is "a bot may propose and may not approve its own proposal"; evidence-domain.md § The MCP specification puts the human-in-the-loop duty on the client, which the server cannot verify; evidence-domain.md § The same sources warn that human approval degrades at volume
- **Confidence**: medium

### Batch: limits, identity, undo

- **Decision**: A token-agent batch covers duplicate pairs only, as the existing route does, and keeps the per-item outcome shape. Each id runs through the single-item token path, so a batch grants nothing its members' rulings do not grant, and a gated member becomes a proposal. A token call is capped at 50 ids (the low end of Wikidata's 50 to 250 trial range); the session cap stays 500. The server issues a `batch_id`, stored on every ledger row and in each audit row's detail. Undo is a unit operation, `POST /kbs/{id}/review/agent-batches/{batch_id}/revert`, which reverts every not yet reverted merge of that batch best-effort with per-item outcomes; keeps need no undo. Finalized token writes are rate limited per token and base from the ledger (200 per rolling hour as a named constant), answering `agent_rate_limited`. No idempotency key is added: a replay meets each store function's state check and returns `already_decided`.
- **Runner-up**: Opening the existing batch to tokens with its 500 cap and size-only `batch` field. It lost because one injected instruction would become up to 500 merges with no handle to find or undo the set, and comparable systems finalize batches only where the batch has an identity and a unit undo.
- **Evidence**: evidence-capability-map.md § `review/batch` decides duplicate pairs only, one action per call, up to 500 ids, with per-item results; evidence-pitfalls.md § `review/batch` is 1–500 ids, one action, not atomic, with per-item audit rows and no batch undo; evidence-similar.md § Batches on Wikidata are undoable as a unit, by anyone, with partial failure; evidence-similar.md § Wikidata lets an approved bot finalize edits, but gates the task, not each edit; evidence-pitfalls.md § MCP is stateless here, re-authenticates every POST, and has no rate limit or idempotency key; evidence-domain.md § The batch route applies one action to up to 500 duplicate pairs, each through the single-item path
- **Confidence**: medium

### Verification stack

### Agent-authority policy

- **Decision**: The per-operation table below (option 1), ruled by the owner on 2026-11-18 (see User rulings). A token agent finalizes keep, mapping decisions, the kind-word decision and the consistency check or inference run; it finalizes merge, duplicate-pair batches and reverts of token-agent merges only behind the server gate named in each row, and a held call becomes a proposal; every other Review write is propose only. Nods on pending facts stay with people (charter veto). The options not chosen were propose only for every operation, and finalize only what has an exact routed undo.
- **Runner-up**: Option 2, propose only for every operation. The evidence does not prefer it because the product's gated governor decided 97.7 percent of 589 labelled pairs on its own, approval by tired reviewers is a documented failure, and no bulk human path exists outside duplicates; it remains fully viable and is what the charter's fallback already assumes.
- **Evidence**: evidence-domain.md § Per-operation reversibility at 3d307f6; evidence-domain.md § The product's stated rule is "act alone only on what can be undone inside the graph; hold what leaves it"; evidence-domain.md § Nods are excluded from every agent by two decision records; evidence-domain.md § The product's own measurements show an agent merging on its own is wrong at a low, non-zero rate, and blind acceptance propagates; evidence-domain.md § Published agent-security guidance says an agent that reads untrusted input and can change state should not act autonomously; evidence-similar.md § Per-operation precedents across comparable systems; evidence-pitfalls.md § OWASP lists human approval and downstream authorization as the mitigations for this exact pattern; evidence-pitfalls.md § Documented incidents show untrusted content causing agent writes under the user's own credentials
- **Confidence**: medium

- **Pitfalls → tasks**: Each known trap is assigned to the task that must dodge it.
  - Ungated person merge path → the merge task calls `hold_for_merge` on the token branch only and proves a held pair becomes a proposal while the session path is unchanged.
  - Token rows read as human precedent → the ledger and precedent task adds `decided_token`, the audit-detail exclusion and the skipped `after_human_decision`, with the wave-1 test above.
  - Governance fuse tripped or bypassed by a token → the revert task restricts finalized reverts to token-agent merges and adds the per-token breaker computed from the ledger.
  - Merge revert does not recall derivations, violations, exports or answers → the ADR and the tool descriptions say so; criterion 7 is verified on graph state only.
  - Batch of 500 with no identity → the batch task enforces the 50-id token cap, issues `batch_id`, and delivers the unit revert with per-item outcomes.
  - Batch audit rows silently missing (`unwrap_or_default` on the snapshot, discarded `audit::record` results) → the token branch treats a failed snapshot or audit write as a failed item, because attribution is a success criterion.
  - Lost races return generic `NotFound` or `Conflict` → every token write task maps them to `already_decided`.
  - No rate limit on MCP or the API → the batch task adds the per-token ledger-based limit; a request already running is not stopped by revocation, which the cap bounds.
  - Retrying agent grows the proposal queue → the proposal-store task ships the partial unique index and `already_proposed`.
  - Proposer approving its own proposal → the proposal answer route takes `AuthUser` only, with a test that a write token is refused.
  - Approval fatigue on a large base → the proposal-store task ships the session-only bulk answer; the roadmap should not defer it past the first propose-only operation.
  - Alignment total omits implication rules → the read task returns the section's true total and tests paging to the last rule item.
  - Refused MCP calls carry no stable code → the MCP task returns the REST codes in the tool error.
  - Activity shows raw action strings and "AI adjudicator" or "a removed user" for machine actors → the attribution task adds labels for token rows only; existing machine-actor rendering is out of scope.
  - Decisions section omits violation, defect, alignment and errata actions → accepted; Agent History and Activity carry them. No change to the Decisions filter.
  - Server crate has no `lib.rs` and tests live in `src/` → token tests are sibling `*_tests.rs` files in `crates/utopia-server/src/api/`; tasks that both edit `review_routes.rs`, `mcp.rs` or `resolution.rs` cannot run concurrently.
  - Backend build reads `web/src/docs/` → documentation tasks that touch `web/src/docs/mcp.md` rebuild the server in their Verify.
  - Shared database across worktrees → every task Verify names its own database; no task relies on a database migrated by another.
  - Number collision with upstream → each landing task re-checks 0128 and 0076 against upstream before commit.
