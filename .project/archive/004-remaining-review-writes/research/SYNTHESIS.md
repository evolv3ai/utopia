### Governor answer: its own proposable operation, a token entry beside the governor's route, the tool review_governor

- **Decision**: An agent proposes an answer to a governor decision through a new ledger operation `governor.answer` whose target is the `agent_decisions` id (`target_kind` `agent_decision`, `target_key` the id), payload `{action: merge|keep|revert, rationale}`, policy row `AgentOperation::AnswerGovernor`. The token entry is a new route `POST /kbs/{id}/review/agent/{decision_id}/propose`; the MCP tool is `review_governor`. The governor's own route is not edited. This rules the recorded conflict: the table row "propose only" (user ruling, INTENT scope in, edge E6) is met by the new entry, and "the governor's own decision route stays session-only" (program synthesis, ADR 0076 decisions 9 and 12, the 401 assertion at `review_token_reads_tests.rs:1099`) holds to the letter. Two added routes are not a parallel route tree; M003 added three routes where no person's handler fitted, and a dated ADR 0076 revision records these. The call changes neither the governor's row, the pair nor the fuse and starts no govern round (E6). At propose time the decision's status and the stored action must form one of the person's three shapes, otherwise the person's code `agent_answer` is answered (E4); a decision that is not `proposed` or `applied`, or a `proposed` decision whose review row is no longer pending, answers `already_decided` (E3). Approval runs the person's governor answer as that person with rationale `None` (the token's sentence stays on the proposal), writes no `token_id` key and adds `agent_proposal` to the audit detail, so precedent, sibling supersession, the govern round and the fuse are the person's.
- **Runner-up**: (a) No separate operation, the row met by merge, keep and revert proposals on the pair. It lost because it fails SC6 as written: no call yields `proposed` for this row, a keep finalizes, and only two of the four answer shapes settle the governor's row. (b) A token branch on `review/agent/{decision_id}`. It lost because it contradicts the settled sentence of the program synthesis and changes a pinned assertion, while the separate entry changes none.
- **Evidence**: evidence-domain.md § Finding: D1, § Finding: D2, § Finding: D3, § Finding: D5, § Finding: D7, § Finding: D8; evidence-pitfalls.md § Finding: P3, § Finding: P4, § Finding: P5, § Finding: P6; evidence-stack.md § Finding: S10; evidence-codebase.md § Finding: F12
- **Confidence**: medium

- **Decision**: Every operation except the nod and the governor answer enters through the person's route with a token branch, as M003 did: the extractor becomes `SessionOrToken`, `if let Some(token) = caller.pat` returns the `review_ops` answer before any session code, every path of the branch returns, and the session code below is unchanged. This covers `close_fact`, `confirm_fact`, `reject_fact`, `resolve_conflict`, `decide_violation`, `decide_defect`, `decide_errata`, `decide_alignment_phrase`, `decide_alignment_rule`, `decide_mapping`, `run_consistency_check`, `run_inference`, `ontology_routes::decide_proposal` and `question_routes::adopt`. A proposal answers HTTP 200 with `{ok: true, outcome: "proposed", action_id, reason: "propose_only", explanation}` plus `code: "already_proposed"` when it met an open one; the two Alignment handlers answer a token 200 and keep 202 for a session. The nod route `POST /kbs/{id}/review/pending/{pending_id}` and `GET /kbs/{id}/review/pending?chunk_id=` are not edited and keep answering a token 401; a token's proposed answer to a pending fact enters by a new route `POST /kbs/{id}/review/pending/{pending_id}/propose`, body `{action: confirm|reject}`. This rules the recorded conflict between "handlers change extractor in place" and a separate entry for the nod: the charter veto on weakening the nod gate outranks the program synthesis, edge E17 allows the nod route to answer a token as before, a slip in a shared nod handler would be a veto breach by a request byte-identical to a person's, and the unchanged 401 assertions are the standing guard.

### Malformed body and the order of refusals

- **Decision**: A person's handler that takes `Json` today keeps that extractor, exactly as the shipped M003 handlers `decide`, `batch` and `manual_merge` do, so a session's answer to any body is byte-equal. A body that does not deserialize is therefore answered by the extractor for every caller before the scope check; this is an accepted, documented exception to "scope, base, role, then the request". For a body that deserializes the order in the token branch is fixed: `authorize_write` (scope, base, role), then shape checks of the body (unknown action, `bad_resolution`, `bad_status`), then the target state read (not found, `already_decided`), then the state-dependent body checks with the person's codes (`close_at_required`, `interval_inverted`, `unknown_property`, `fact_required`), then the landing. The token branch shares the handler's request struct, so E4 holds by construction. The two new routes parse raw bytes after `authorize_write` and answer `invalid_body` as the M003 token revert does.
- **Runner-up**: Changing every opened handler to raw bytes so a refused caller always hears the scope code first. It lost because it changes what a signed-in person gets for a malformed body (prohibition N12) on fourteen handlers, and the M003 routes already ship the exception.
- **Evidence**: evidence-pitfalls.md § Finding: P14; evidence-stack.md § Finding: S9, § Finding: S13; code read by the decider: `crates/utopia-server/src/api/review_routes.rs:1268-1300` (raw bytes on revert only because a session sends no body) and `:1346-1365` (`manual_merge` keeps `Json`)
- **Confidence**: medium

### Target state: one typed read for the propose-time check and for superseded

- **Decision**: One store function per target kind reads the target scoped by base and answers `Open`, `Decided` or `Missing`; no error text is matched for any new operation, and M003's `target_gone` stays as it is for the three merge operations only. The same read is used twice. At propose time: `Missing` is not found, `Decided` is `already_decided`, `Open` lands the proposal (E3). At approval, before the person's function runs: `Missing` or `Decided` closes the proposal `superseded` and changes nothing else (E8). Per kind: confirm fact — missing or invalidated is `Missing`, no decided state; reject fact and close fact — invalidated is `Decided`, and a live fact that already has an end is not found for close as the person's route answers; a store `Ok(None)` from the close is treated as stale and never as success; conflict — `fact_conflicts.status` open, both facts live, and the two fact ids equal to those stored in the payload; violation — `axiom_violations.status` open and, for `fact_retracted` and `fact_closed`, the body's fact still live and open; defect — `ontology_defects.status`; errata — `errata_actions.status` held; ontology proposal — `ontology_proposals.status` open and agent-proposed; phrase and rule — row presence only (E8: applied while the target exists); pending fact — row presence only (E17: unknown or already nodded is not found); governor — `agent_decisions.status` proposed or applied in the shape the stored action needs, and for the proposed shapes the review row still pending; mapping (finalize) — status equal to the requested one is `already_decided` (E13). After the read, a typed `NotFound` from the person's function also closes the proposal `superseded` only where that function is one guarded statement or one transaction (confirm fact, reject fact, defect, conflict, ontology adopt). Any other error, an uncoded conflict included, is returned and leaves the proposal open; the next answer meets the typed read. No guard is added to a function a person calls. The remaining check-then-act windows across processes are recorded in ADR 0076 as known limits beside the two it lists.
- **Runner-up**: Mapping the person's errors per kind as the rule. It lost because five kinds give an answer that cannot carry the meaning: success that did nothing (close fact, ontology reject), `NotFound` after a committed step (violation `fact_retracted`), a double apply (errata), a 422 that means decided and a 409 after the pair changed (governor); and the person's errors collapse unknown and decided, so E3 cannot be built from them. A status-guarded store variant per kind also lost: it adds a second writer beside the person's function, against edge E7.
- **Evidence**: evidence-pitfalls.md § Finding: P7, § Finding: P8, § Finding: P9, § Finding: P12; evidence-codebase.md § Finding: F5, § Finding: F22
- **Confidence**: medium

### Unruled points: content drift, a body invalid at approval, contradicting proposals

- **Decision**: (1) Content drift under an unchanged id closes the proposal `superseded` for the two kinds where a stored fingerprint exists to compare, following the M003 queue-merge precedent: a conflict whose two fact ids differ from the payload's, and an ontology proposal whose stored payload differs from the fingerprint taken at propose time. Phrase and rule proposals are not checked for drift, because edge E8 rules that they apply while the target exists. (2) A body that was valid when proposed and is refused at approval (`interval_inverted`, `not_open`, `unknown_property` and the like) is returned to the person with the person's code, as that item's `code` in a bulk answer; the proposal stays open until a person declines it, as the M003 shell does. No rule closes it without a person. (3) Contradicting open proposals are legal where edge E2 allows them and get no ordering rule: each approval is judged by the typed read at its own turn, a bulk answer walks ids in request order, and a later one whose target was decided by an earlier one closes `superseded`. Confirm then reject of one live fact both apply, as two decisions of that person, which a person can already do by hand. The operation strings above remove the contradiction for a pending fact, a conflict, an ontology proposal and a governor decision.
- **Runner-up**: Closing a proposal whose body became invalid as `superseded`. It lost because edge E8 names only a target that is gone or decided, some of these refusals are temporary, and a sweep without a person is out of scope. Closing sibling proposals when one is approved also lost for the same scope reason.
- **Evidence**: evidence-pitfalls.md § Finding: P10, § Finding: P11, § Finding: P17, § Finding: P5; evidence-codebase.md § Finding: F5
- **Confidence**: medium

- **Confidence**: high

### Agent rail badge

- **Decision**: `review::counts` keeps `agent` as the governor's proposed count and gains one key `agent_token_proposals`, the number of open token proposals of the base, emitted only when above zero. The web badge shows the sum of the two (driver D128, edge E11). No existing count changes value and an exact-key assertion on a base with no open proposal keeps passing.
- **Runner-up**: Adding the open token proposals into `agent`. It lost because it changes the value of an existing count that session and M003 assertions read on bases with open proposals.
- **Evidence**: evidence-codebase.md § Finding: F18, § Finding: F20; evidence-pitfalls.md § Finding: P1
- **Confidence**: medium

### The specification's rate-limit duty against edge E5

- **Decision**: Edge E5 stands: no count limit is added to propose-only calls. What bounds them inside the intent's limits is already decided: one open proposal per base, operation and target, a repeat that writes no row, a refused call that writes no ledger row, and the 200 limit on everything that finalizes. Nothing more is built. ADR 0076 and `mcp.md` state that propose-only calls are bounded by stored rows and not by call count.
- **Runner-up**: A separate call-count limit on propose-only tools. It lost because edge E5 rules that a propose-only call is never answered `agent_rate_limited`, a new limit or code would change an approved criterion, and a configurable limit is out of scope.
- **Evidence**: evidence-domain.md § Finding: D19; evidence-stack.md § Finding: S1; evidence-codebase.md § Finding: F6
- **Confidence**: medium
