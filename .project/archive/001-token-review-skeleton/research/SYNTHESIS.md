## Settled

- Stack — Rust workspace (axum 0.8, sqlx, Postgres 16 with pgvector) and the React 19 / Vite web app; no new framework or service (CHARTER.md Constraints; program SYNTHESIS.md Settled, Stack)
- Token identity — a personal token acts as its owner, scope only narrows, every call re-checks scope and writes an audit row; no base-level machine token or service account (program SYNTHESIS.md Settled, Token identity; ADR 0014 decisions 1, 2, 5)
- Authority ruling — the owner ruled "Option 1: the recommended per-operation table" (program SYNTHESIS.md User rulings, 2026-11-18); in this milestone only its keep row (finalize) is reachable by a token (ROADMAP.md M001 Scope in)
- Enforcement point — the authority policy is enforced by the server, never by the MCP client, tool annotations or elicitation (program SYNTHESIS.md Settled, Enforcement point)
- Token access to Review routes — existing handlers change extractor from `AuthUser` to `SessionOrToken` in place; reads call `require_reader_kb`; writes call `require_write(Some(kb_id))` first, then `require_kb(.., Role::Editor)`; codes `token_read_only`, `token_kb_out_of_scope`, new `token_owner_below_editor`, new `already_decided`; a session caller's requests and responses are unchanged (program SYNTHESIS.md Decisions, Token access to Review routes)
- Token-agent write path — each write handler branches on the caller: a session caller runs today's code unchanged; a token caller goes to one shared server-side policy function living with the `execution_gate` module, holding the compiled-in per-operation table and returning `applied`, `held` or `proposed` (program SYNTHESIS.md Decisions, Token-agent write path and the ADR 0027 execution gate)
- One implementation for REST and MCP — each Review operation is one server function taking the resolved caller (owner id, token id, base id), called by the REST token branch and the MCP tool; MCP gains `review_list` (section parameter, existing 1 to 200 page clamp), `review_item`, and one write tool per operation family; read tools for any token reaching the base with an owner at least Viewer, write tools listed and callable only with scope `write` and an owner at least Editor; a refused write returns a tool error whose structured content carries the REST code; annotations are hints only; elicitation is not used (program SYNTHESIS.md Decisions, MCP tools over the same implementation)
- Read surface — tokens read through the handlers the Review tab already uses: `GET /kbs/{id}/review?queue=` and `GET /kbs/{id}/review/summary`; item evidence is the list item's own fields plus the already token-open `facts/{fact_id}/evidence` and `entities/{entity_id}` reads; in this milestone only Duplicates and Overview are served to tokens (program SYNTHESIS.md Decisions, Read surface; ROADMAP.md M001 Scope in and Scope out)
- Attribution of record — `audit_events.actor_id` stays the owner; every token Review write adds `detail.token_id` and a `detail.token_name` snapshot taken at insert time; the agent's name is the token's name, shown as "owner via token name"; the stored HTTP `User-Agent` is returned marked as declared and never read for authorization; MCP `clientInfo` is not parsed (program SYNTHESIS.md Decisions, Attribution of record)
- Ledger and display — new table `token_agent_actions` is the ledger of every token-agent Review action; Agent History (`queue=agent`) returns the governor's `agent_decisions` rows unchanged plus ledger rows told apart by a `source` field; Activity keeps its Admin-only session route, `AuditEventView` gains optional `token_id`, `token_name` and declared client, and the web app labels token rows only (program SYNTHESIS.md Decisions, Agent History and Activity)
- Precedent isolation — token-agent decisions are never human precedent: the governor's precedent queries and `settled_by_people` exclude audit rows whose detail carries a token id and review rows marked by a new nullable `resolution_reviews.decided_token` column; `after_human_decision` is not called for a token decision; `review/agent/{decision_id}` stays session-only (program SYNTHESIS.md Decisions, Governor precedent and the governance fuse)
- Closed until later milestones — token merge, manual merge, revert and batch, the proposal store, the other eleven sections, proof routes, section totals, the rate limit and the breaker are not built here (ROADMAP.md M001 Scope out; CHARTER.md veto 1)

## For the planner

- **Wave-1 blockers**: the verification ground (existing `token_read` and `token_setup` tests pass on the compose instance with `UTOPIA_TEST_REQUIRE_DB=1`; per-run databases isolate two builds with different migration sets; Windows-side `cargo` reaches `127.0.0.1:1517`), ADR 0076 written with the ruled authority table after a fresh check of upstream numbers, and the store's ontology module read to confirm or correct "adoption has no undo" before the record is final. The database-backed test that a token keep does not lower the governor's bar, does not settle a pair in `settled_by_people` and starts no govern round belongs with the ledger and precedent work, as early as its schema allows.
- **Walking skeleton**: Duplicates end to end over both surfaces, then one write through the policy layer. Read slice: a personal token lists `queue=duplicates` and Overview over REST and over MCP `review_list`, gets the same items as a session editor, 404 for a base outside `kb_ids`, and reads an item through `review_item`. Write slice: keep on one duplicate pair with a write token of an editor through the shared operation function and the policy table, producing a `token_agent_actions` row and an audit row with `token_id` and `token_name`, shown in Agent History and Activity as "owner via token name"; a read-scope token answers `token_read_only`, a below-editor owner `token_owner_below_editor`, a repeat `already_decided`; token merge, revert and batch stay refused.
- **Pitfalls → tasks**:
  - Token rows read as human precedent → the ledger and precedent task adds `decided_token`, the audit-detail exclusion and the skipped `after_human_decision`, with the database-backed test.
  - Batch and audit rows silently missing (`unwrap_or_default` on the snapshot, discarded `audit::record` results) → the token branch treats a failed snapshot or audit write as a failed action.
  - Lost races return generic `NotFound` or `Conflict` → the token keep maps them to `already_decided`.
  - Refused MCP calls carry no stable code → the MCP task returns the REST codes in the tool error.
  - Activity shows raw action strings → the attribution task adds labels for token rows only; existing machine-actor rendering is out of scope.
  - Server crate has no `lib.rs` and tests live in `src/` → token tests are sibling `*_tests.rs` files in `crates/utopia-server/src/api/`; tasks that both edit `review_routes.rs`, `mcp.rs` or `resolution.rs` cannot run concurrently.
  - Backend build reads `web/src/docs/` → a documentation task that touches `web/src/docs/mcp.md` rebuilds the server in its Verify.
  - Shared database across worktrees → every task Verify names its own database; no task relies on a database migrated by another.
  - Number collision with upstream → each landing task re-checks 0128 and 0076 against upstream before commit.
  - Every Verify runs in a fresh sidecar worktree with nothing installed → web Verify commands install first (`pnpm install --frozen-lockfile`).
