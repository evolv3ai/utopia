## Finding: The person's Review write paths never ask the ADR 0027 merge gate

- **Claim**: `execution_gate::hold_for_merge` / `impact_of` / `hold` are called from exactly three places: the batch adjudicator, the governor, and the errata recorder. `resolution::decide_review`, `decide_reviews` (batch), `merge_entities` (manual merge) and the `agent_answer` merge branch do not call them. A merge that arrives through the Review routes lands even when it would create a `functional` contradiction, rewrite derived facts, or touch an entity named in chat answers.
- **Source**: `crates/utopia-store/src/execution_gate.rs:1-14, 108-151`; callers by grep of `execution_gate::` over `crates/` (non-test): `crates/utopia-server/src/adjudication.rs:396`, `crates/utopia-server/src/governance.rs:575, 842, 852`, `crates/utopia-store/src/errata.rs:521-537`; ungated human path `crates/utopia-store/src/resolution.rs:1991-2064`, `crates/utopia-server/src/api/review_routes.rs:283-339, 656-702`
- **Confidence**: high
- **Why it matters here**: Opening `decide`, `batch` or `manual_merge` to a token as they stand gives an agent a merge path with fewer checks than the server's own automatic deciders have; ADR 0027 decision 3 names "an agent's calls" as this gate's intended next caller.

## Finding: A merge revert restores the graph but not what the merge sent out of it

- **Claim**: ADR 0027 states that `revert_merge` moves facts back but cannot recall a derivation drawn on the merge, a violation it opened, an export it entered, or a chat answer it was cited in. The code's `revert_merge` is one transaction that moves facts back, un-invalidates the facts the merge invalidated, deletes copied evidence, restores the target's profile and type, and revives the source; a second call returns `Conflict("Merge already reverted")`.
- **Source**: `docs/decisions/0027-an-automatic-merge-is-gated-by-what-it-can-undo.md:7-11, 15-27`; `crates/utopia-store/src/resolution.rs:2487-2629`
- **Confidence**: high
- **Why it matters here**: Charter success criterion 7 ("the graph returns to its state before the merge") is satisfiable, but "every merge revertible" does not make an agent merge harmless; the residue outside the graph is the cost of a finalized wrong merge.

## Finding: Rejecting a fact and confirming a fact have no undo function in this checkout

- **Claim**: `graph::reject_fact` calls `temporal::retract`, which sets `invalidated_at` and recomputes the timeline; `graph::confirm_fact` overwrites `confidence` with 1.0. No `temporal::restore`, `temporal::set_confidence` or `temporal::undo_rewrite` exists in `crates/` (grep for `temporal::restore|fn restore|undo_reject|unreject` matches only document restore and CLI restore). ADR 0043's undo table names those functions, and its status line says the code was withdrawn ("no code on `dev`"). The only record of the prior confidence is the `fact.confirm` audit row's snapshot.
- **Source**: `crates/utopia-store/src/graph.rs:2147-2179`; `crates/utopia-store/src/temporal.rs:852-877`; `crates/utopia-server/src/api/review_routes.rs:28-51, 560-606`; `docs/decisions/0043-every-review-queue-is-governed.md:3, 37-50, 76`
- **Confidence**: medium
- **Why it matters here**: Reject and confirm are the two fact operations the charter lists for agents, and today neither can be taken back through the API; a finalize ruling for them would be a ruling for an irreversible write.
- **Limits**: High for the absence of these functions in `crates/` at this HEAD; medium that no other route restores a rejected fact (only `review_routes.rs` and the store modules above were read). The finding is rated at the lower level.

## Finding: A rejected nod is remembered forever and blocks the same proposal

- **Claim**: `pending::reject` inserts into `rejected_facts` and deletes the pending row; `pending::propose` returns `Outcome::Rejected` for any later proposal with the same (subject, predicate, object entity, phrase). Literal-value facts are not checked. No route in `review_routes.rs` removes a `rejected_facts` row.
- **Source**: `crates/utopia-store/src/pending.rs:142-165, 566-585`; `docs/decisions/0015-recording-a-sentence-is-not-asserting-a-fact.md:45-52`
- **Confidence**: medium
- **Why it matters here**: An agent talked into rejecting a nod suppresses a true fact on every later extraction, silently; ADR 0043 decision 1 and ADR 0025 both keep nods with people ("an agent nodding for them would turn a remark into an assertion").
- **Limits**: High for the block on re-proposal; medium for "no removal route" (checked in `review_routes.rs` only). The finding is rated at the lower level.

## Finding: Token-agent decisions would be read by the governor as human precedent

- **Claim**: The governor's precedent queries select `audit_events` rows `WHERE actor_id IS NOT NULL` and `resolution_reviews` rows `WHERE decided_by IS NOT NULL`. Every Review handler writes the audit row with `user.id` and passes `user.id` as `decided_by`. A token acts as its owner (ADR 0014 decision 1), so an agent's merge or keep made with a token is indistinguishable from a person's in those queries. Precedent lowers the governor's auto-apply bar from `AUTO_CONF` 0.85 to `SUPPORTED_CONF` 0.75, `settled_by_people` follows a prior same-pair decision outright, and `after_human_decision` enqueues a `govern` round after each decision.
- **Source**: `crates/utopia-store/src/governance.rs:20-25, 89-117, 157-160, 522-571, 575-616`; `crates/utopia-server/src/governance.rs:978-1013`; `crates/utopia-server/src/api/review_routes.rs:303-336`; `docs/decisions/0025-governance-reads-the-ledger-before-it-decides.md:17` (decision 1 heading: "The ledger is the precedent, and only people write it")
- **Confidence**: high
- **Why it matters here**: A single injected agent decision does not stay single: it becomes precedent that the governor applies automatically to other pairs of the same name or type pair. Attribution (success criterion 6) needs a marker the precedent queries can exclude, or agent finalizes break ADR 0025 decision 1.

## Finding: The governor's fuse does not count token-agent merges, and a token-agent could trip it

- **Claim**: The fuse turns governance off after `FUSE_REVERTS` = 2 reverts in `FUSE_WINDOW_DAYS` = 7 of merges recorded in `agent_decisions`. A merge made through `decide_review` or `manual_merge` writes no `agent_decisions` row, so reverting it is not counted. Conversely `agent_answer` with `revert` and `revert_merge` both call `fuse`; two reverts of governor merges switch the base's governance off and write `kb.updated {governance:false, via:"fuse"}`.
- **Source**: `crates/utopia-store/src/governance.rs:1059-1061`; `crates/utopia-server/src/governance.rs:908-976`; `crates/utopia-server/src/api/review_routes.rs:395-417, 640-641`
- **Confidence**: high
- **Why it matters here**: The existing circuit breaker gives no protection against a misled token-agent's merges, and opening `revert` to agents gives them an indirect write to a base setting (governance on/off) that ADR 0014 decision 6 keeps session-only.

## Finding: `review/batch` is 1–500 ids, one action, not atomic, with per-item audit rows and no batch undo

- **Claim**: `batch` requires Editor, accepts 1..=500 review ids (`BATCH_MAX`) with one action (`merge` or `keep`) and one optional rationale, and calls `decide_reviews`, which loops `decide_review` per id outside any shared transaction; a failing id is returned with its error and the rest proceed. One audit row per successful id carries `"batch": <count>` but no batch identifier. The snapshot query's failure is swallowed (`unwrap_or_default`), in which case decisions are applied with no audit rows; every `audit::record` result is discarded (`let _ =`). Undo is per merge through `revert_merge`; a kept pair is undone only by a later merge. It covers duplicates only: no batch route exists for facts, conflicts, nods, errata or alignment.
- **Source**: `crates/utopia-server/src/api/review_routes.rs:471-558`; `crates/utopia-store/src/resolution.rs:1906-1929`; route table `crates/utopia-server/src/api/mod.rs:532-585`
- **Confidence**: high
- **Why it matters here**: One injected instruction can become up to 500 ungated merges in one call, each needing its own revert, with no id to find the set by; charter scope lists `batch` as an agent write.

## Finding: `review/agent/{decision_id}` answers the governor through the person's path, in three shapes

- **Claim**: `agent_answer` requires Editor and matches on (decision status, action): a `proposed` decision answered `merge`/`keep` calls `decide_review` and settles the row `accepted` or `overridden`; an `applied` merge answered `revert` calls `revert_merge`, settles `reverted` and checks the fuse; an `applied` keep answered `merge` calls `merge_entities` with reason "overrode agent keep" and settles `overridden`. Any other combination returns `agent_answer` invalid. The steps (graph change, `settle`, audit row) are separate statements, not one transaction. Each writes an audit row under the person carrying `agent_decision`.
- **Source**: `crates/utopia-server/src/api/review_routes.rs:341-469`; `docs/decisions/0025-governance-reads-the-ledger-before-it-decides.md:58-60`
- **Confidence**: high
- **Why it matters here**: This route is the designed human check on the server's own agent; a token-agent that may finalize it is one model approving another model's proposal, and the result is stored as a person's answer and precedent.

## Finding: A person, the governor and a token-agent can race on one item with partial guards

- **Claim**: `decide_review` reads the row with `status = 'pending'`, checks `locked_by_agent`, merges, then updates the review with `WHERE id = $1` only (no `AND status = 'pending'`), across separate statements. `merge_entities` checks `merged_into` before opening its transaction. A second caller gets `NotFound` (review no longer pending), `Conflict("Entity already merged")`, or `Conflict("The agent is deciding this pair right now…")`. Errata answers are guarded atomically by `UPDATE … WHERE status = 'held'`. `confirm_fact` on an already-confirmed fact succeeds again and writes a second audit row; `reject_fact` on an already-rejected fact returns `NotFound`.
- **Source**: `crates/utopia-store/src/resolution.rs:1998-2064, 2144-2164`; `crates/utopia-store/src/governance.rs:954`; `crates/utopia-store/src/errata.rs:780-824`; `crates/utopia-store/src/graph.rs:2148-2179`
- **Confidence**: medium
- **Why it matters here**: Agents call faster and in parallel; the replies to a lost race are generic (`NotFound`), which a retrying agent cannot tell from a wrong id, and the charter asks for stable error codes on refusals.
- **Limits**: High for the statements as written in the source; medium for the practical race window (not exercised; no test run). The finding is rated at the lower level.

## Finding: MCP is stateless here, re-authenticates every POST, and has no rate limit or idempotency key

- **Claim**: `mcp::handle` authenticates on every POST (`revoked_at IS NULL` and expiry in the SQL), declares no session id, ignores `initialize` params (so `clientInfo` is not read), and writes one `mcp.tool_called` audit row per `tools/call` whose detail is only `{tool}`. Grep for `rate_limit|RateLimit|tower_governor|ConcurrencyLimit|429|idempoten` over `crates/utopia-server/src` matches only model-client, connector and alerting files, none in `api/mcp.rs`, `api/review_routes.rs`, `api/mod.rs` or auth. The only layers in the router are response headers, body limits, CORS, trace and client-context capture.
- **Source**: `crates/utopia-server/src/api/mcp.rs:9-18, 84-112, 171-261`; `crates/utopia-store/src/tokens.rs:155-178`; `crates/utopia-server/src/api/mod.rs:80-92, 284, 400-404, 508, 625-658`
- **Confidence**: medium
- **Why it matters here**: Revocation takes effect on the next request, but a request already running (a 500-id batch) completes; a replayed write call is deduplicated only by each store function's own state check; and the MCP specification says servers MUST rate limit tool invocations.
- **Limits**: High for what `mcp.rs` and `tokens.rs` do; medium for "no rate limit anywhere on the API" (grep-based). The finding is rated at the lower level.

## Finding: The MCP specification puts access control and rate limiting on the server and treats the human check as a client SHOULD

- **Claim**: MCP 2025-06-18 "Tools → Security Considerations": servers MUST validate all tool inputs, implement proper access controls, rate limit tool invocations and sanitize tool outputs; clients SHOULD prompt for user confirmation on sensitive operations. The same page: "there SHOULD always be a human in the loop with the ability to deny tool invocations." The schema says all `ToolAnnotations` (`readOnlyHint`, `destructiveHint` default true, `idempotentHint` default false) are hints and "Clients should never make tool use decisions based on ToolAnnotations received from untrusted servers." The transports page gives no exactly-once or idempotency guarantee for `tools/call`; it says disconnection "SHOULD NOT be interpreted as the client cancelling its request."
- **Source**: https://modelcontextprotocol.io/specification/2025-06-18/server/tools ; https://modelcontextprotocol.io/specification/2025-06-18/schema (ToolAnnotations) ; https://modelcontextprotocol.io/specification/2025-06-18/basic/transports
- **Confidence**: high
- **Why it matters here**: The server cannot rely on the agent's client to ask its user before a Review write, and cannot assume a write call arrives once; the finalize-versus-propose rule has to be enforced server-side, as the charter already requires.

## Finding: OWASP lists human approval and downstream authorization as the mitigations for this exact pattern

- **Claim**: OWASP LLM01:2025 defines indirect prompt injection as occurring "when an LLM accepts input from external sources, such as websites or files", lists "Manipulating critical decision-making processes" as an impact, and prescribes "Require human approval for high-risk actions" and least privilege. OWASP LLM06:2025 names three root causes (excessive functionality, permissions, autonomy) and prescribes "Require user approval… to approve high-impact actions before they are taken", "Complete mediation: Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed or not", and marks logging and rate limiting as measures that limit damage but do not prevent it.
- **Source**: https://genai.owasp.org/llmrisk/llm01-prompt-injection/ ; https://genai.owasp.org/llmrisk/llm062025-excessive-agency/
- **Confidence**: high
- **Why it matters here**: Audit rows and revert (charter scope items "Attribution" and "Merge revert") are in OWASP's damage-limiting class, not its preventing class; only the propose path and server-side gates are in the preventing class.

## Finding: Documented incidents show untrusted content causing agent writes under the user's own credentials

- **Claim**: (a) Rehberger, 2024-05-22: text in a connected Google Doc and in an uploaded image caused ChatGPT's memory tool to write persistent memories without the user asking ("each bullet point became a memory"), and a prompt injection could delete all memories; his recommendations include "Do not automatically invoke tools once untrusted data… enter the chat" and limiting how many memories can be inserted at once. (b) Invariant Labs, 2025-05-26: a malicious GitHub issue read by an agent through the GitHub MCP server caused it to open a pull request leaking private-repository data, using the user's token; the post states the flaw is "not a flaw in the GitHub MCP server code itself" and notes "many users already opt for an 'Always Allow' confirmation policy when using agents."
- **Source**: https://embracethered.com/blog/posts/2024/chatgpt-hacking-memories/ ; https://invariantlabs.ai/blog/mcp-github-vulnerability
- **Confidence**: medium
- **Why it matters here**: Both are the charter's stated risk in production form: a knowledge store written on the strength of text the agent just read, and a correctly scoped token that did not help because the agent was the authorized party. Client-side confirmation was the control that users had switched off.
- **Limits**: High that the write-ups say this (both are the researchers' own reports); medium as evidence of how often such attacks occur. The finding is rated at the lower level.

## Finding: Open extraction writes confidence 1.0 for every statement except chart or image descriptions

- **Claim**: The only non-test extraction write is `extraction_open.rs`, which sets `confidence = origin_ceiling(&chunk.origin, 1.0)`; `origin_ceiling` returns the value unchanged unless `origin == "described"`, in which case it caps at `DESCRIBED_CEILING = LOW_CONFIDENCE_BELOW - 0.05` = 0.70. The comment reads: an open statement has no model-reported confidence; it says "the document said so". Pushed statements also enter at 1.0 (ADR 0054). Other writers: typed rows copy their statement's confidence, implication-rule rows are 0.9 (`materialize.rs:568`), errata additions are 0.9 (`errata.rs:659-667`), a confirmed nod carries the pending row's value (1.0 or 0.70 from the same path), and a person's confirm sets 1.0. The `insert_fact(…, 0.9)` calls in `extraction.rs` are inside `mod tests` (file's `#[cfg(test)] mod tests` starts at line 428).
- **Source**: `crates/utopia-server/src/extraction_open.rs:535-537, 614-653`; `crates/utopia-server/src/extraction.rs:93-106, 428-429`; `docs/decisions/0054-a-source-may-push-statements-in-the-open-contract.md:80`; `crates/utopia-store/src/materialize.rs:247, 535, 568`; `crates/utopia-store/src/errata.rs:659-667`; `crates/utopia-store/src/pending.rs:322-330, 442-450`; `crates/utopia-store/src/graph.rs:2150`
- **Confidence**: high
- **Why it matters here**: "Every fact at 100%" on the owner's base is the designed behaviour of the open-graph extraction path (ADR 0044 decision 2), not a defect of that deployment; confidence carries no per-fact signal an agent or a policy could use.

## Finding: The Low confidence queue selects `confidence < 0.75`, so it holds only described-origin facts

- **Claim**: `LOW_CONFIDENCE_BELOW` is 0.75; the list query is `f.invalidated_at IS NULL AND f.confidence < $2`, and the count query adds `AND derived_by_rule IS NULL` (the list does not, so the badge and the list can differ when derived rows are below the line). Given the writers above, only facts from `described` chunks (0.70) and typed rows materialised from them fall below 0.75.
- **Source**: `crates/utopia-store/src/review.rs:18-20, 78-80`; `crates/utopia-store/src/graph.rs:2072-2102`; `crates/utopia-server/src/api/review_routes.rs:108-117`; `docs/decisions/0040-a-chunk-says-where-its-words-came-from.md:98-108`
- **Confidence**: medium
- **Why it matters here**: The section is still in scope for success criterion 1 but will list nothing on a base with no image- or chart-described chunks; where it is non-empty, every item is a model's reading of a picture, the content ADR 0040 says is most often misread, so an agent `confirm` there carries the least independent evidence.
- **Limits**: High for the queries as written; medium for "empty on the owner's base" (their corpus and build were not inspected). The finding is rated at the lower level.

## Finding: There is no general proposal store; the propose path exists for three item kinds only

- **Claim**: Proposals wait today in `pending_facts` (remember, deduplicated by `AlreadyAsserted` / `AlreadyPending` / `Rejected`, attributed by `proposed_by` and `proposed_token`), `agent_decisions` with status `proposed` (duplicate pairs only; ADR 0025 decision 5: "a partial unique index allows one open proposal per pair"), and `errata_actions` with status `held`. ADR 0043's widening of `agent_decisions` to facts and conflicts (migration 0058) was withdrawn with PR #699. `remember` over MCP writes a memory document and enqueues extraction on every call, with no size or call cap visible in the tool.
- **Source**: `crates/utopia-store/src/pending.rs:119-199`; `crates/utopia-store/src/review.rs:88-100`; `docs/decisions/0025-governance-reads-the-ledger-before-it-decides.md:56`; `docs/decisions/0043-every-review-queue-is-governed.md:3, 76`; `crates/utopia-server/src/api/tools.rs:991-1047`
- **Confidence**: medium
- **Why it matters here**: A propose-only ruling for confirm, reject, conflict resolution or revert has nowhere to land yet; each needs a pending shape with a uniqueness rule, or a retrying agent grows the queue without bound.
- **Limits**: High for which proposal stores exist; medium for "no cap on remember" (`memory::append_episode` was not read). The finding is rated at the lower level.

## Assigned questions — answers

- Which operations may an agent finalize and which may it only propose? Gather the precedents (ADR 0015 nod, ADR 0025 governor, ADR 0027 merge gate, ADR 0043 governed queues, ADR 0044 errata gate) and each operation's reversibility, including what a wrong action sends out of the graph. Decide proposes a per-operation table; the owner rules on it (Delegated, driver D003). This ruling is a `NEEDS-USER` item at decide. → Failure-mode evidence per write, no ruling made. **Merge (decide/batch/manual, and `agent_answer` merge)**: ungated on the person's path (`execution_gate` has three callers, none of them these; `resolution.rs:1991-2064`); graph-reversible by `revert_merge` (`resolution.rs:2500-2629`) but derivations, violations, exports and chat answers drawn while it was live are not recalled (ADR 0027 lines 7-11); becomes governor precedent (`store/governance.rs:89-117`). **Keep**: changes no fact, undone by a later merge (ADR 0027 decision 2), but is also read as precedent and can lower or block later automatic merges (`store/governance.rs:553`). **Revert merge**: guarded against double revert; counts toward the fuse and can switch governance off after two (`server/governance.rs:908-976`). **Confirm fact**: sets confidence 1.0, no undo function, prior value only in the audit snapshot (`graph.rs:2148-2162`). **Reject fact / violation `fact_retracted`**: invalidates and recomputes timelines, queues typed recompute, no restore function in `crates/` (`graph.rs:2171-2179`, `temporal.rs:852-877`). **Nod confirm**: enters the graph by the extraction path with temporal reconciliation (`pending.rs:289-330`); ADR 0043 decision 1 and ADR 0025 keep nods with people. **Nod reject**: permanent block via `rejected_facts` (`pending.rs:142-165`). **Conflict resolve / close fact**: rewrites rows; conflict path commits fact rewrite, resolution and audit together and re-checks the conflict is open (ADR 0043, 2026-10-20 note); undo (`undo_rewrite`) is not in the code. **Errata approve**: executes a retraction, revision or addition that the errata gate deliberately held (`errata.rs:516-550`: gate hold or `unflagged`); **errata reject** only records. **Alignment kind word**: already open to write tokens (ADR 0014 decision 6; `review_routes.rs:1370-1426`). Existing guards: ADR 0027 gate (automatic deciders only), ADR 0025 hard rules and fuse (governor rows only), errata quote-in-document check and gate (`errata.rs:497-550`), `pending_facts` nod gate, `rejected_facts`, per-action audit rows (results discarded with `let _ =`). Outside sources put human approval and server-side authorization in the preventing class and logging/rate limits in the damage-limiting class (OWASP LLM01:2025, LLM06:2025; MCP tools spec).
- What do `review/batch` and `review/agent/{decision_id}` do today, and what does a batch of agent actions do to the confused-deputy risk? → `batch`: Editor session, 1–500 review ids, one `merge|keep` action, per-id `decide_review` with no shared transaction, per-id outcomes returned, one audit row per success tagged with the batch size but no batch id, duplicates queue only, undo only by reverting each merge (`review_routes.rs:471-558`, `resolution.rs:1906-1929`). `agent/{decision_id}`: Editor session answers a governor row — accept or override a proposal, revert an applied merge (fuse checked), or merge over an applied keep — through the person's store functions, non-transactionally, with audit rows carrying `agent_decision` (`review_routes.rs:341-469`). Effect on the confused-deputy risk: a batch multiplies one injected instruction by up to 500 ungated merges per request with no rate limit in front of it (`mcp.rs`, `api/mod.rs` layers), each merge is then read as human precedent that the governor applies to further pairs (`store/governance.rs:89-117, 522-571`), token revocation cannot stop a request already running (`tokens.rs:155-178` authenticates once per request), and clean-up is one revert per merge with no batch handle. No source was found that measures injection success rates for batch tools specifically.
- The spec reports every fact at 100% confidence on the owner's base. Does that leave the Low confidence section empty for agents, and is it extraction behaviour? The program does not scope a fix. → Yes to both, with one exception. It is extraction behaviour: the open-graph path writes `origin_ceiling(origin, 1.0)` for every statement (`extraction_open.rs:537`), pushes enter at 1.0 (ADR 0054 line 80), confirmed nods carry the same value, a person's confirm sets 1.0, and implication and errata rows are 0.9. The exception is statements from `described` chunks (a model's description of an image or chart), capped at 0.70 (`extraction.rs:97-106`). The queue selects `confidence < 0.75` (`review.rs:20, 78-80`; `graph.rs:2091`), so it is empty unless the base holds described-origin chunks. Paths that write 1.0: document extraction, memory extraction (after the nod), `statements` pushes, and `confirm_fact`. The owner's deployed build and corpus were not inspected.
- Largest assumption, challenged: that an agent reading untrusted base content can be allowed to finalize anything safely. If it cannot, the program still delivers reads plus proposals for every operation; research should say what that leaves a person to click on a large base. → No source found supports "safe to finalize" as a general property; OWASP LLM01/LLM06 and the two incident reports say the preventing controls are human approval and server-side mediation. The code shows the least costly finalize candidates by reversibility are keep (no fact changes) and merges that the ADR 0027 gate would pass (graph-reversible, nothing sent out) — but only if those merges are routed through the gate and excluded from precedent, neither of which the person's path does today. Costs of propose-only, from the code: (1) proposal storage exists only for nods, duplicate pairs and errata (`pending.rs`, `agent_decisions`, `errata_actions`); other operations need a new pending shape with a uniqueness rule or retries grow the queue; (2) no rate limit or idempotency key on MCP or the API, so volume is bounded only by per-item state checks; (3) two audit rows per agent write over MCP (`mcp.tool_called` plus the action row); (4) revocation applies per request, not mid-request; (5) races return `NotFound` / `Conflict` without a stable "already decided" code. What is left for a person to click: duplicates can be answered 500 per request through `review/batch`; every other queue (nods, conflicts, unconfirmed, low confidence, violations, defects, mappings, errata, alignment phrases and rules, governor proposals) is one request per item, listed at most 200 per page (`review_routes.rs:86`, route table `api/mod.rs:532-585`). The item counts on the owner's base are not known to this research.
