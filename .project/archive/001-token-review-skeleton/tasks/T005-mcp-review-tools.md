# T005 — Serve review_list, review_item and review_keep over MCP through the shared operation layer

## Context

The MCP endpoint (`POST /api/v1/kbs/{kb_id}/mcp`, `crates/utopia-server/src/api/mcp.rs`) serves eleven read tools and `remember`, and nothing that touches Review. The settled design is one implementation for REST and MCP: each Review operation is one server function taking the resolved caller, and both the REST token branch and the MCP tool call it. T004 delivered those functions for the token API (`review_ops::list`, `summary`, `keep`). This task adds the MCP tools over them: `review_list` (a `section` parameter, the existing 1 to 200 page clamp; Duplicates and Overview in this milestone), `review_item` (one duplicate pair's evidence, the fields of its card), and `review_keep` (the one write). Read tools are listed for any token that reaches the base with an owner at least Viewer; the write tool is listed only with scope `write` and an owner at least Editor. A refused write returns a tool error whose structured content carries the same stable code as REST. Tool annotations are hints only; elicitation is not used; MCP `clientInfo` is not parsed. Whether the MCP path can really share the REST implementation is a named medium-confidence risk; this task's parity tests are its proof.

## Approach

- Put the three tool definitions (name, description, input schema, annotations) and their dispatch in a new module `crates/utopia-server/src/api/review_tools.rs`, declared in `crates/utopia-server/src/api/mod.rs`, and call it from `mcp.rs`. Do not add them to `chat::tools_schema` or `tools::dispatch` (`crates/utopia-server/src/api/chat.rs`, `tools.rs`): those are shared with the in-app chat assistant, which must be offered no Review tool. `chat::check_call` takes a schema value and can guard the arguments of the new tools; `tools::ToolResult` (`new`, `structured`, `error`) is the result type `mcp.rs` already renders.
- `mcp.rs` builds a `ReviewCaller` from what `authorize` already returns (the user, the `Authenticated` token, the base) and calls `review_ops`. Authorization, policy, ledger and audit stay inside `review_ops`; the tool layer only maps arguments and results.
- Listing: `review_list` and `review_item` appear in `tools/list` for every caller `authorize` lets in; `review_keep` appears only when `can_write` is true (INTENT prohibition N5, criterion SC5: the keep tool is not listed to a caller who is refused the keep).
- Calling `review_keep` without the right must still reach `review_ops::keep` and come back as a tool result with `isError: true` and `structuredContent` `{"code": "<code>", "message": "<the REST message>"}` — `token_read_only` or `token_owner_below_editor`, and `already_decided` for a repeat — not as the JSON-RPC `-32601` error that an unlisted `remember` gets today. The `remember` branch, its `-32601` answer and its listing rule stay exactly as they are.
- Results: on success `structuredContent` is the same JSON the token API returns for the same token — for `review_list` with `section: "duplicates"` the `{"counts","queue","items"}` object of `review_ops::list`, with `section: "overview"` the summary object of `review_ops::summary`, for `review_keep` the object of `review_ops::keep`. Any other section goes to `review_ops::list`, which refuses it with `unknown_queue`. Every error of an operation becomes a tool error whose `structuredContent.code` is the code the REST error body would carry; a 404 carries `not_found`.
- Page size: `limit` and `offset` are optional integers passed through to `review_ops::list`, which clamps. The input schema must not reject an out-of-range `limit`: a value below 1 is served as 1 and above 200 as 200, as the session route does (`review_routes.rs`, `q.limit.unwrap_or(REVIEW_PAGE).clamp(1, 200)`).
- `review_item` takes `{"id": "<review id>"}`. Add the operation `review_ops::item` and a store lookup in `crates/utopia-store/src/resolution.rs` that returns one pending pair of the base as the same `ReviewItem` the list assembles (reuse the private `assemble_reviews`; do not change `list_reviews`, `decide_review` or `decide_reviews`). An id that is not a pending duplicate pair of this base — unknown, decided, or belonging to another base — gets one and the same not-found tool error with no evidence field.
- N3 (judgment prohibition). Must not: return Review items, counts or evidence over MCP to a token whose `kb_ids` exclude the base. Detail: the reviewer checks that `review_list` and `review_item` pass the same reader check as the token API and give such a token no item, count or evidence. So both read tools go through `review_ops`, whose reader check is the token API's; do not add a second, MCP-only check that could drift, and do not loosen `authorize`.
- The existing per-call audit row `mcp.tool_called` stays (one per call, also for refused calls). A keep over MCP additionally writes its `review.keep` audit row inside `keep_duplicate_pair`; do not write a second one.
- Annotations: `readOnlyHint: true` on the two read tools; on `review_keep` `readOnlyHint: false`, `destructiveHint: false`, `idempotentHint: false`. They are hints; no code path reads them.
- Tests go through the router (`POST /api/v1/kbs/{kb}/mcp` and the REST routes with `oneshot`), in `review_mcp_tests.rs`, wired with `#[cfg(test)] #[path = "review_mcp_tests.rs"] mod ...;` in `mcp.rs` or declared in `mod.rs`. `mcp_tests.rs` shows how to send `tools/list` and `tools/call`. For the failed audit write (E11) one way is a temporary `BEFORE INSERT` trigger on `audit_events` that raises only `WHEN (NEW.kb_id = '<this test's base>')`, with a unique name, dropped at the end of the test even when it fails; choose another injection if it is safer, but the failure must happen inside the real keep path.
- Documentation: extend `web/src/docs/mcp.md` — the three tools in the tools table, who sees and may call each, the sections served in this milestone, the structured error codes, and one sentence that a keep made by an agent is recorded under the token's owner and the token's name. Remove nothing about `remember` and its nod.
- Existing tests that prove the signed-in person's paths and `remember` are unchanged must pass without modification: do not edit `crates/utopia-server/src/api/mcp_tests.rs` or any file under `crates/utopia-store/tests/store/`. They are in `files` only because the Verify runs them.
- Conventions (bind this task): explanatory code comments in Chinese; tests and migrations named as sentences; user-facing error strings in English with a stable `code`; an ADR precedes any public-API or data-model change (ADR 0076 from T002 covers these tools; if a tool or code must differ from it, stop with `NEEDS-ORCHESTRATOR`); new migration numbers start at 0128 and ADR numbers at 0076, re-checked against upstream `deeplethe/utopia` `dev` and its open pull requests before landing — this task adds no numbered file; migration SQL idempotent; one behaviour-sentence commit subject with a DCO `Signed-off-by`; nothing is sent to `deeplethe/utopia` or a deployed instance.

## Interface contract

- `crate::api::review_ops` (file `crates/utopia-server/src/api/review_ops.rs`): `pub(crate) struct ReviewCaller { pub user: utopia_core::models::User, pub token: utopia_store::tokens::Authenticated, pub kb_id: Uuid }`; `pub(crate) async fn list(state: &AppState, caller: &ReviewCaller, section: &str, types: Option<&str>, limit: Option<i64>, offset: Option<i64>) -> Result<serde_json::Value, AppError>`, where section `"duplicates"` returns `{"counts","queue","items"}` exactly as `GET /api/v1/kbs/{kb_id}/review?queue=duplicates` returns it to a session (limit default 10, clamped to 1..=200; offset floored at 0) and any other section returns `AppError::invalid("unknown_queue", ..)`; `pub(crate) async fn summary(state: &AppState, caller: &ReviewCaller) -> Result<utopia_core::models::ReviewSummary, AppError>`; `pub(crate) async fn keep(state: &AppState, caller: &ReviewCaller, review_id: Uuid, rationale: Option<&str>) -> Result<serde_json::Value, AppError>`, returning `{"ok": true, "outcome": "applied", "action_id": "<ledger row id>"}`. Every function authorizes inside itself: `list` and `summary` return `AppError::NotFound` when the owner is not at least Viewer of the base or the token's `kb_ids` exclude it; `keep` checks the token's scope first (`token_read_only`, then `token_kb_out_of_scope`), then the owner's role (`AppError::CodedForbidden { code: "token_owner_below_editor", .. }` below Editor), then the policy, then calls `keep_duplicate_pair`, and does not call `after_human_decision`.
- Token-open REST routes, all under `/api/v1` with `Authorization: Bearer utp_pat_…`: `GET /kbs/{kb_id}/review?queue=duplicates` (optional `types`, `limit`, `offset`), `GET /kbs/{kb_id}/review/summary`, and `POST /kbs/{kb_id}/review/{review_id}` with body `{"action":"keep","rationale":<string or null>}` answering `{"ok": true, "outcome": "applied", "action_id": "<uuid>"}`. Refusals: 404 for a base outside the token's `kb_ids` on the reads; 422 `unknown_queue`; 403 `token_read_only`, `token_kb_out_of_scope`, `token_owner_below_editor`, `token_operation_not_open`; 409 `already_decided`.
- Session regression test: file `crates/utopia-server/src/api/review_session_unchanged_tests.rs`, test function `a_session_editor_gets_todays_duplicates_overview_keep_merge_and_batch_responses`.
