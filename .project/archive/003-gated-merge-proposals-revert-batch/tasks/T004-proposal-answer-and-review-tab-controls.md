# T004 — A signed-in editor answers agent proposals in Agent History, sees them on the Duplicates and Merges cards, and reverts an agent merge that the Merges section shows as owner via token name

## Context

After wave 2 a held or propose-only token call waits as an open row of `token_agent_actions` and nobody can answer it. This task gives the signed-in editor the answer, in the API and in the Review tab, and makes the Merges section tell an agent's merge from a person's. Ground truth at `6c52ce8`: `review_routes::agent_answer` (434, `AuthUser`) answers the governor's proposals and is the model for a session-only answer route; `review_routes::batch` shows the bulk shape (`BATCH_MAX` 500, 422 `batch_size`, one outcome per id). The session handlers `decide` (351 to 420), `manual_merge` (737) and `revert_merge` (689) show what a person's merge and revert do beside the store call: a best-effort `audit::record`, then `governance::after_human_decision` or `governance::after_revert`. `resolution::assemble_reviews` (1789) fills `ReviewItem.proposal` from the governor's `agent_decisions`; `resolution::list_merges` (2669) returns `MergeLogView` rows (`utopia-core/src/models.rs:1080`) with `merged_by_name`. In the web app `web/src/pages/Review.tsx` (2,347 lines) renders Agent History at 2270 to 2287 through `TokenAgentRow`, the Duplicates card at 143 to 249 (governor chip at 189 to 196) and `MergeRow` at 484 to 522 (prints `S.review.mergedBy(name)` or `mergedByAi`, with the Revert button); mutations `decide`, `agentAnswer`, `batch`, `revert` sit around 1446 to 1594. `web/src/pages/TokenAgentRow.tsx` exports `viaToken`, `tokenOperationLabel`, `TokenAgentRow` and has no control; `TokenAgentRow.test.ts` (45 to 52) asserts a row has no button at all. Labels live in `web/src/i18n/en.ts` (2139 to 2147: `tokenVia`, `tokenOperations`, `tokenOutcome`) and `zh.ts` (1874 to 1879). vitest renders components statically and clicks nothing, so the click path is walked in a browser at final review (PLAN.md Surface contract).

## Approach

- Store (`token_agent_actions.rs`): `proposal(pool, kb_id, id)`, a guarded close `answer(pool, kb_id, id, state, user_id, merge_id)` that updates only a row with `state` null and reports whether it won (the loser is `already_decided`), and the lookups the read shapes need. The `undone` read (an `applied` merge row whose merge has `reverted_at`) is computed in the ledger list query and `history_row`; nothing is written when a person reverts.
- Answer handlers in `review_routes.rs`, `AuthUser` only, Editor required, routes registered in `crates/utopia-server/src/api/mod.rs`. Approve: check the target can still be decided (the review is pending, neither entity is merged away, the merge is not reverted); if not, close `superseded`. Otherwise run the person's path with the person as actor and no gate, then close `approved` with the merge id. To avoid a second copy of a session handler's statements you may move them, unchanged, into a private function that the session branch and the answer handler both call; the session answers must not change (`review_session_unchanged_tests` proves it). Approving a revert proposal calls `governance::after_revert` exactly as the session revert does, so the fuse counts it as today (E15). The bulk handler answers each id through the single-answer function and returns one outcome per id.
- Read shapes: add the optional `agent_proposal` to `ReviewItem` and `agent` and `agent_proposal` to `MergeLogView` (`skip_serializing_if` on `None`), filled in `assemble_reviews` and `list_merges` from the ledger. The session handler `revert_merge` is not edited.
- Web. `TokenAgentRow` gains optional `onApprove` and `onDecline` props and renders Approve and Decline only for an open proposal (outcome `held` or `proposed`, no `state`) when the props are given; it shows the gate reason and the later state through labels. Agent History in `Review.tsx` gets a selection of open proposals with "Approve selected" and "Decline selected" (one bulk request). New file `web/src/pages/AgentProposal.tsx` exports `AgentProposalChip` (the open proposal on a Duplicates card, beside the governor's chip, and on a Merges row) and `MergeActor` (the "merged by" text of a Merges row: "owner via token name" when `agent` is present, today's text otherwise); `Review.tsx` uses both. `api.ts` gains the two answer calls and the new optional fields. `en.ts` and `zh.ts` gain a label for every operation (`review.merge`, `merge.manual`, `merge.revert`), every reason code and every state (`approved`, `declined`, `superseded`, `undone`); no code is shown raw. No button is added for the unit revert of a batch.

## Interface contract

- **Ledger (delivered by T001).** Migration `migrations/0129_a_token_agent_action_keeps_its_reason_its_batch_its_merge_and_its_later_state.sql` adds to `token_agent_actions`, all nullable: `gate_reason TEXT`, `batch_id UUID`, `merge_id UUID`, `target_key TEXT`, `state TEXT` (checked: `approved`, `declined`, `superseded`, `undone`), `state_at TIMESTAMPTZ`, `state_by UUID`; and the partial unique index `token_agent_actions_open_proposal_idx` on `(kb_id, operation, target_key)` where `outcome IN ('held','proposed') AND state IS NULL`. `CURRENT_SCHEMA_VERSION` is 115. The ledger `operation` and the audit `action` share one name: `review.keep`; `review.merge` (`target_kind` `review`, `target_id` and `target_key` the review id); `merge.manual` (`target_kind` `entity`, `target_id` the target entity, `target_key` the two entity ids in ascending order joined by `|`); `merge.revert` (`target_kind` `merge`, `target_id` and `target_key` the merge id). `outcome` is `applied`, `held` (a gate hold) or `proposed` (propose only). `gate_reason` is one of `identity`, `contradiction`, `derived`, `answered`, `kept_by_person`, `reverted_merge` (with `held`) or `merge_by_person`, `merge_by_governor`, `breaker` (with `proposed`). `merge_id` on an `applied` merge row is the merge it made, on a `merge.revert` row the merge it targets, on an `approved` merge proposal the merge the person's approval made. `payload` holds the full request. An open proposal is a row with outcome `held` or `proposed` and `state` null. `approved`, `declined` and `superseded` are stored by the answer route with `state_at` and `state_by` (the answering person). `undone` is never stored: an `applied` merge row reads `state` `undone`, with `state_at` the revert time, whenever `entity_merges.reverted_at` of its `merge_id` is set, so a person's revert through today's unchanged handler shows it with no write. A merge made by a token agent is a merge named by `merge_id` of a row with operation `review.merge` or `merge.manual` and outcome `applied`; a merge reverted by a token is one named by an `applied` `merge.revert` row; every other reverted merge was reverted by a person or the governor's fuse.
- **Audit rows of token writes (delivered by T001).** Written in the transaction of the ledger row, `actor_id` the token's owner, detail carrying `token_id`, `token_name`, `action_id` (the ledger row), `merge_id` when a merge is named and `batch_id` when the call is a batch member: `review.merge`, `merge.manual` and `merge.revert` for an applied call (target the review, the target entity, the merge), and `agent.proposal` (`target_kind` `agent_action`, target the ledger row, detail also `operation`, `outcome`, `reason`) for a held or propose-only call.
- **Store functions (delivered by T001; no later task changes a signature).** In `utopia_store::execution_gate`: `Hold` gains the variants `KeptByPerson` and `RevertedMerge` and the method `Hold::code(&self) -> &'static str` returning the `gate_reason` code; `hold_for_token_merge(pool: &PgPool, kb_id: Uuid, a: Uuid, b: Uuid) -> AppResult<Option<Hold>>` asks `hold_for_merge` first, then the kept-pair lookup, then the reverted-merge lookup, both by entity ids in either order. `hold_for_merge`, `agent_ruling` and the signature of `agent_policy` are unchanged, and `hold_for_merge` never returns a new variant. In `utopia_store::token_agent_actions`: `pub struct TokenWrite { pub kb_id: Uuid, pub owner_id: Uuid, pub token_id: Uuid, pub rationale: Option<String>, pub batch_id: Option<Uuid>, pub breaker: bool }`; `pub struct TokenWriteOutcome { pub action: TokenAgentAction, pub existing: bool, pub follow_up_error: Option<String> }` (`existing` is true when the call met an open proposal and wrote nothing; `follow_up_error` is set when the merge committed and a later follow-up step failed); `merge_duplicate_pair(pool: &PgPool, w: &TokenWrite, review_id: Uuid) -> AppResult<TokenWriteOutcome>`, `merge_entity_pair(pool: &PgPool, w: &TokenWrite, source: Uuid, target: Uuid) -> AppResult<TokenWriteOutcome>` and `revert_merge(pool: &PgPool, w: &TokenWrite, merge_id: Uuid) -> AppResult<TokenWriteOutcome>`. Each asks the gate or the propose-only rule itself before it writes; with `breaker` true a merge or a revert lands `proposed` with reason `breaker`. Errors: `AppError::NotFound` (unknown id or another base); `AppError::CodedConflict` with code `already_decided` (decided pair, lost race, entity already merged away, merge already reverted); `AppError::Invalid` with code `self_merge`; the uncoded `AppError::Conflict` that `keep_duplicate_pair` returns for a pair a running governor round holds. `TokenAgentAction` gains `gate_reason`, `batch_id`, `merge_id`, `state`, `state_at`, `state_by`; an Agent History ledger row gains the keys `reason`, `batch_id`, `merge_id`, `state`, `state_at`, each present only when it has a value, so the row of a keep has exactly the keys it has today. `resolution::merge_entities` and `resolution::revert_merge` keep their signatures and behaviour. `governance::type_pair_stats` no longer counts, as reverted, a merge made by a token agent and reverted by a token.
- **Token revert over REST (delivered by T003).** `POST /api/v1/kbs/{kb_id}/merges/{merge_id}/revert` takes `SessionOrToken`; a token may send `{"rationale":"…"}` or no body. A token caller goes to `review_ops::revert_merge(state, caller, merge_id, rationale, batch_id)` (`pub(crate) async`, `Result<serde_json::Value, AppError>`). Answers, HTTP 200: applied `{"ok":true,"outcome":"applied","action_id":…,"merge_id":…}` when a token agent made the merge; `{"ok":true,"outcome":"proposed","action_id":…,"reason":"merge_by_person"|"merge_by_governor"|"breaker","explanation":…}` otherwise, plus `"code":"already_proposed"` on a repeat. Refusals: 403 `token_read_only`, 403 `token_owner_below_editor`, 404 for an unknown merge id or one of another base, 409 `already_decided` for a merge already reverted. A session caller runs today's code and gets today's answer.
- **Proposal answer, session only (delivered by T004).** `POST /api/v1/kbs/{kb_id}/review/agent-proposals/{proposal_id}` with body `{"action":"approve"|"decline"}` and `POST /api/v1/kbs/{kb_id}/review/agent-proposals` with body `{"ids":[…],"action":"approve"|"decline"}` (1 to 500 ids) take `AuthUser` only and need an Editor of the base; every personal token gets 401. Single answer, HTTP 200: `{"ok":true,"state":"approved"|"declined"|"superseded"}` plus `"merge_id"` when a merge was made or reverted; 409 `already_decided` for an answered proposal; 404 for an unknown id. Bulk answer, HTTP 200: `{"answered":n,"outcomes":[{"id","state","merge_id","code","error"}]}` in request order, one per id; 0 or 501 ids is 422 `batch_size` and answers nothing. Approval runs the person's own path with the person as actor and no gate (`resolution::decide_review` with `merge`, `resolution::merge_entities`, or `resolution::revert_merge`, with the audit row and the governance follow-up today's session handler makes), and that audit row's detail carries `agent_proposal` (the ledger row id). A target that can no longer be decided closes the proposal `superseded` and applies nothing. Decline and supersede write audit rows `agent.proposal.declined` and `agent.proposal.superseded` with the person as actor.
- **Read shapes for proposals and merges (delivered by T004).** A Duplicates item gains `agent_proposal` `{"id","operation","reason","owner_name","token_name","created_at"}` when an open `review.merge` proposal targets it or an open `merge.manual` proposal names its two entities; a merges-list row gains `agent` `{"action_id","owner_name","token_name"}` when a token agent made the merge and `agent_proposal` (same shape as on an item) when an open `merge.revert` proposal targets it. Each key is serialized only when it has a value, so every other row is byte-for-byte what it is today, for session, token and MCP readers alike.
