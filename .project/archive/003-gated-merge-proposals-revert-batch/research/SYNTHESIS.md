## Settled

- Stack — Rust workspace (axum 0.8, sqlx, Postgres 16 with pgvector) and the React 19 / Vite web app; no new framework or service (CHARTER.md Constraints; program SYNTHESIS.md Settled, Stack)
- Token identity — a personal token acts as its owner, scope only narrows, every call re-checks scope; a write needs scope `write` and an owner at least Editor; no base-level machine token (program SYNTHESIS.md Settled, Token identity; CHARTER.md veto 3)
- Authority — the owner's ruling "Option 1: the recommended per-operation table": Merge (queue decision and manual merge), Revert merge and Batch (duplicate pairs) are finalize behind the server gate; a held call becomes a proposal; Keep finalizes; every other Review write is propose only and is not built here (program SYNTHESIS.md Decisions, Agent-authority policy; User rulings)
- Token access — the queue decision, manual merge, revert and batch handlers change extractor from `AuthUser` to `SessionOrToken` in place; a session caller's branch runs today's code unchanged; writes check `require_write` first, then Editor; codes `token_read_only`, `token_owner_below_editor`, `already_decided`, `already_proposed`, and `agent_rate_limited` with HTTP 429 (program SYNTHESIS.md Decisions, Token access to Review routes)
- Write path and gate — a token caller is passed to the one shared policy function that lives with the `execution_gate` module and holds the compiled-in table; every token merge, single, manual or batch member, calls `hold_for_merge` before `merge_entities`; a hold becomes a proposal carrying the gate's reason, never an error and never a merge; the gate also holds a pair a person kept or that has a reverted merge; a pass applies the same store function the person's path calls; the table is not a per-base setting (program SYNTHESIS.md Decisions, Token-agent write path and the ADR 0027 execution gate)
- One implementation for REST and MCP — each Review operation is one server function in `review_ops` taking the resolved caller; the REST token branch and the MCP tool both call it; MCP gains one write tool per operation family (merge, revert, batch), listed and callable only with scope `write` and an owner at least Editor; a refused call returns a tool error carrying the REST code (program SYNTHESIS.md Decisions, MCP tools over the same implementation)
- Proposal store — a held or propose-only call waits as a `token_agent_actions` row with outcome `held` or `proposed`, holding the full request and changing no fact, entity, review row, retrieval or reasoning; a partial unique index allows one open proposal per base, operation and target; a repeat returns the existing proposal with `already_proposed`; a person answers in the Agent History section through a route that takes `AuthUser` only; approval runs the existing session store function with the person as actor and `detail.agent_proposal` naming the proposal; a target that can no longer be decided closes the proposal `superseded`; a person may answer many proposals in one request, capped at 500 (program SYNTHESIS.md Decisions, Proposal store)
- Ledger — `token_agent_actions` gains the columns this milestone first writes: later state (`approved`, `declined`, `superseded`, `undone`), gate reason, batch id, undo reference such as the merge id, answering person and timestamps; Agent History returns governor rows unchanged plus ledger rows told apart by `source`; Activity keeps its Admin-only session route (program SYNTHESIS.md Decisions, Agent History and Activity)
- Attribution — an agent action is recorded as owner plus token: `actor_id` stays the owner, every token Review write adds `detail.token_id` and a `detail.token_name` snapshot, shown as "owner via token name" (program SYNTHESIS.md Decisions, Attribution of record)
- Governor and fuse — token decisions are never human precedent; `after_human_decision` is not called for a token decision; the governor's decision route stays session-only; a token never finalizes a revert of a person's or the governor's merge, so it cannot trip the governance fuse; the per-token breaker is computed from the ledger with the governor's constants: two reverts by a person of one token's finalized merges on a base within seven days make that token propose-only on that base for the rest of the window (program SYNTHESIS.md Decisions, Governor precedent and the governance fuse)

## For the planner

- **Wave-1 blockers**: the assumptions that could invalidate the plan are in the store. (1) The ledger can hold everything this milestone writes — later state, gate reason, batch id, merge link, answerer, one open proposal per target — by migration, with `CURRENT_SCHEMA_VERSION` bumped. (2) A token merge can be made atomic with its ledger and audit rows although `merge_entities` commits and then runs follow-up steps that can fail (INTENT.md N2), without changing what the person's path does. (3) The gate can answer the two new holds, a pair a person kept and a pair with a reverted merge, by entity ids. (4) A merge followed by its revert returns facts, entities and evidence to their state under the comparison of INTENT.md E12. (5) The precedent rule of E25 holds end to end: a token merge, and a merge made and reverted by tokens, move no governor read and start no govern round. If any of these fails the write surface is redesigned before a route opens.
- **Walking skeleton**: one gated queue merge end to end — a write token of an editor merges a duplicate pair the gate passes over the token API and over the MCP merge tool (ledger row `applied`, audit row with token id and name, the merge named in the response), the same call on a held pair lands one proposal and changes nothing, and the token reverts its own merge — then the proposal answer and its Review tab controls, manual merge, batch with its unit revert, limit and breaker, attribution in the Merges section and Activity, and documentation.
