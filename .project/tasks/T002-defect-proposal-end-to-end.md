# T002 — Open the defect decision to a token as a proposal over REST and MCP, answered by a person

## Context

This is the walking skeleton: one propose-only operation, the defect decision, runs end to end over REST and MCP and is approved or declined by a signed-in person, with the generic pieces every later family reuses. The M003 patterns to follow are in `crates/utopia-server/src/api/review_routes.rs` and `crates/utopia-server/src/api/review_ops.rs`: the token branch of `review_routes::decide` (lines 353 to 374), `review_ops::authorize_write` (lines 69 to 84), `review_ops::keep` (lines 361 to 388), `review_ops::guard` (lines 317 to 344) and the answer dispatch `review_routes::answer_proposal` (lines 850 to 918). Today `decide_defect` (`crates/utopia-server/src/api/review_routes.rs` line 1734) takes a session only, calls `reasoning::decide_defect`, writes the audit row `defect.decided` and refuses an unknown resolution with `bad_resolution`; `answer_proposal` dispatches on three merge operations and answers 500 for any other. The one test function that pins 401 on eight routes this milestone opens is `a_token_cannot_nod_and_every_review_write_outside_the_ruled_table_answers_401` (`crates/utopia-server/src/api/review_token_reads_tests.rs` lines 1049 to 1194); this task is its only editor in the plan.

## Interface contract

- **Ledger names of this milestone (delivered by T001).** No migration; `token_agent_actions` keeps its columns. A propose-only row has `outcome` `proposed` and `gate_reason` `propose_only`; a finalized row has `outcome` `applied`. Operation and `target_kind`: `fact.confirm`, `fact.reject`, `fact.close` (`fact`); `conflict.resolve` (`conflict`); `violation.decide` (`axiom_violation`); `defect.decide` (`ontology_defect`); `errata.decide` (`errata_action`); `alignment.phrase` (`phrase_binding`); `alignment.rule` (`implication_rule`); `pending.nod` (`pending_fact`); `governor.answer` (`agent_decision`); `mapping.decide` (`concept_mapping`) — each with the row's own id as `target_id` and as `target_key`; `ontology.proposal` (`ontology_proposal`, `target_id` the id of the `ontology_proposals` row, `target_key` the section and the key joined by `:`); `alignment.kind_word` (`type_binding`, `target_id` the base id, `target_key` the normalized kind word); `consistency.check` and `inference.run` (`knowledge_base`, `target_id` and `target_key` the base id). There is one open proposal per base, operation and `target_key`. `payload` keys: `request` (the full request body), `target_label` (words naming the target), `action` (when the operation has one), `why` (the rationale, when given) and `fingerprint` (conflict and ontology proposal only). `action` codes: `confirm`, `reject`, `close` (the three fact operations); `close`, `retime_new`, `keep`, `reject_new` (conflict); `fact_retracted`, `fact_closed`, `axiom_relaxed`, `accepted` (violation); `fixed`, `accepted` (defect); `approve`, `reject` (errata and rule); `bind`, `none` (phrase and kind word); `adopt`, `reject` (ontology proposal); `confirm`, `reject` (pending fact); `merge`, `keep`, `revert` (governor answer); `confirmed`, `rejected` (mapping); the two runs have none.
- **Store functions for proposals and finalized rows (delivered by T001; no later task changes a signature).** In `crates/utopia-store/src/token_agent_actions.rs`: `pub struct Proposal<'a> { pub operation: &'a str, pub target_kind: &'a str, pub target_id: Uuid, pub target_key: &'a str, pub payload: serde_json::Value }`; `pub async fn propose(pool: &PgPool, w: &TokenWrite, p: &Proposal<'_>) -> AppResult<TokenWriteOutcome>` writes in one transaction one `proposed` ledger row and its `agent.proposal` audit row (`target_kind` `agent_action`, detail `operation`, `outcome`, `reason`, `token_id`, `token_name`, `action_id`) and touches no other table; when an open proposal exists for that base, operation and `target_key`, or a second call arrives at the same moment, it writes nothing and returns the open row with `existing` true. `pub async fn record_applied(conn: &mut sqlx::PgConnection, w: &TokenWrite, p: &Proposal<'_>) -> AppResult<TokenAgentAction>` writes one `applied` ledger row on the caller's connection, so it commits or rolls back with the caller's change. `pub fn token_audit_detail(detail: serde_json::Value, action: &TokenAgentAction) -> serde_json::Value` adds `token_id`, `token_name` and `action_id` to an audit detail. `pub async fn open_proposals_for(pool: &PgPool, kb_id: Uuid, target_kind: &str, target_ids: &[Uuid]) -> AppResult<std::collections::HashMap<Uuid, Vec<AgentProposalView>>>` returns the open proposals of those targets, oldest first. `AgentProposalView` gains `action: Option<String>`, serialized only when set. `held_back`, `land_proposal`, the three merge functions, `keep_duplicate_pair`, `answer`, `proposal`, `target_gone` and `finalized_since` keep their signatures and behaviour.
- **Typed target state (delivered by T001).** New module `crates/utopia-store/src/review_targets.rs`: `pub enum TargetState { Open, Decided, Missing }`; `pub async fn target_state(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid, request: &serde_json::Value, fingerprint: Option<&serde_json::Value>) -> AppResult<TargetState>`; `pub async fn fingerprint(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid) -> AppResult<Option<serde_json::Value>>`; `pub async fn target_label(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid, request: &serde_json::Value) -> AppResult<String>`; `pub async fn ontology_proposal_id(pool: &PgPool, kb_id: Uuid, section: &str, key: &str) -> AppResult<Option<Uuid>>`. Every read is scoped by base, so an id of another base is `Missing`, and no error text is matched. Rules: `fact.confirm` — a missing or invalidated fact is `Missing` and there is no `Decided`; `fact.reject` and `fact.close` — an invalidated fact is `Decided`, and for `fact.close` a live fact that already has an end is `Missing`; `conflict.resolve` — `Open` while the conflict's status is open and both facts are live, `Decided` otherwise, and `Decided` when a fingerprint is given and the conflict's two fact ids differ from it; `violation.decide` — `Open` while the violation's status is open and, for the resolutions `fact_retracted` and `fact_closed`, the fact the request names is live and has no end, `Decided` otherwise; `defect.decide` — `Open` while the defect's status is open; `errata.decide` — `Open` while the action's status is held; `ontology.proposal` — `Open` while the proposal's status is open and the ontology agent proposed it, and `Decided` when a fingerprint is given and the stored payload differs from it; `alignment.phrase`, `alignment.rule` and `pending.nod` — `Open` while the row exists and `Missing` otherwise, with no `Decided`; `governor.answer` — `Open` when the decision is `proposed` and its review row is still pending, or the decision is `applied`, and `Decided` otherwise; `mapping.decide` — `Decided` when the mapping's status equals the requested status and `Open` otherwise. `fingerprint` returns the conflict's two fact ids or the ontology proposal's stored payload, and nothing for any other operation.

- **Proposal answer for every operation (delivered by T002; each family task adds its arm).** The two session-only routes `POST /api/v1/kbs/{id}/review/agent-proposals/{proposal_id}` and `POST /api/v1/kbs/{id}/review/agent-proposals` keep `AuthUser`, their bodies and their M003 answers; `review_routes::answer_proposal` gains one arm per operation string and keeps answering 500 for an operation it does not know. That audit row never carries `token_id`, and the token's rationale is never passed as the person's reason. Single answer, HTTP 200: `{"ok":true,"state":"approved"|"declined"|"superseded"}` plus, each only when set, `merge_id` (as today), `job_id` with `"queued":true` (an approved phrase or rule proposal) and `fact_id` (an approved confirm of a pending fact). ## Acceptance criteria

1. A write token of an editor that posts a defect decision over REST, and the same call through the MCP tool `review_defect`, gets HTTP 200 with outcome `proposed` and reason `propose_only`; the defect row, every fact and entity of the base and the count of queued jobs are equal before and after, and one open proposal exists for that defect.
2. A signed-in editor approves the proposal on the single answer route: the defect is decided exactly as that person's own decision decides it, the audit row `defect.decided` has the person as actor and names the proposal, and the proposal reads `approved`; a declined proposal leaves the defect open and reads `declined`.
3. E7 (held-out; ruling: answering needs a signed-in Editor of the base, a proposal already answered answers `already_decided` and nothing changes, approval runs the person's own store function with the person as actor and the proposal named in the audit detail): a viewer session and every token are refused on the answer route, and a second answer is 409 `already_decided` with no new row.
4. An unknown resolution is 422 `bad_resolution`, an unknown defect or one of another base is 404, a decided defect is 409 `already_decided`, and a repeated call returns the open proposal with `already_proposed`; none of these lands a row.
5. `review_defect` is listed only for a write token of an editor, and a read-scope or below-editor caller that calls it gets a tool error with `token_read_only` or `token_owner_below_editor`.
6. A session defect decision returns today's body and writes today's audit row; `a_token_cannot_nod_and_every_review_write_outside_the_ruled_table_answers_401` still asserts 401 for the nod, the governor's route and the pending-chunk read; the seven moved 401 tests pass.
