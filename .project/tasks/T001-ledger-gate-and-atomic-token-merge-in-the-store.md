# T001 — Burn down the store risks: ledger columns by migration 0129, the token merge gate with six holds, a token merge and revert atomic with their ledger and audit rows, and the precedent rule

## Context

M003 opens merge, manual merge, revert and batch to a `write` token of an Editor, each behind the ADR 0027 merge gate, with held calls waiting as proposals. Everything that could invalidate that design is in the store, and this task proves it there before any route opens (program synthesis, wave-1 blockers 1 to 5). Ground truth at `6c52ce8`: the ledger `token_agent_actions` (migration 0128) has `outcome` in `applied`, `held`, `proposed` and no column for a gate reason, a batch, a merge link or a later state, and no unique index on open proposals; `token_agent_actions::keep_duplicate_pair` is the one token write and shows the pattern (governor-lock check, then one transaction: review row locked `FOR UPDATE`, guarded update with `decided_token`, ledger row, `audit::record_on`). `execution_gate::hold_for_merge` has four holds and is called by the adjudicator and the governor only. `resolution::merge_entities` (lines 2181 to 2487) checks `self_merge` and "Entity already merged" before it opens its own transaction, commits, and then runs follow-up steps (signature check, `reconcile_moved_facts`, `refresh_disambiguators`) that can fail after the merge. `resolution::decide_review` (2028) reads a pending row and writes it with no status guard, taking the direction from `merge_direction`. `resolution::revert_merge` (2537) restores facts, evidence and the target's profile, leaves review rows and recorded signature violations, and leaves an untyped target with the type it took. `governance::type_pair_stats` (159 to 196) counts every reverted merge; the other precedent reads already exclude token rows through `NOT_BY_TOKEN` and `decided_token`. `CURRENT_SCHEMA_VERSION` is 114 at `crates/utopia-cli/src/main.rs:85`. Two existing tests in `crates/utopia-store/tests/a_token_keep_is_never_human_precedent.rs` pin what this task changes: `replaying_migration_0128_changes_nothing` asserts the exact column list of `token_agent_actions` (lines 341 to 356), and `the_compiled_table_holds_the_owners_ruling` (982) calls `agent_policy` with `Hold` values. If any of the five proofs fails, stop with `NEEDS-ORCHESTRATOR` and say which: the write surface is redesigned before a route opens.

## Approach

- Migration: one file, `migrations/0129_a_token_agent_action_keeps_its_reason_its_batch_its_merge_and_its_later_state.sql`, idempotent (`ADD COLUMN IF NOT EXISTS`, `CREATE UNIQUE INDEX IF NOT EXISTS`, a guarded check constraint), Chinese header comment as 0128 has. Bump `CURRENT_SCHEMA_VERSION` to 115. Columns, index, operation names and reason codes are fixed by the Interface contract.
- Gate: add the two holds and `hold_for_token_merge` in `execution_gate.rs`. "A pair a person kept": the latest decided review of those two entities, in either order, has status kept with `decided_token` null and a person as decider. "A pair with a reverted merge": any `entity_merges` row between the two entities, in either direction, has `reverted_at` set. Both by entity ids. `hold_for_merge` and its two existing callers behave exactly as before.
- Token merge, atomic (N2 below): give `resolution.rs` a transaction-scoped merge core that `merge_entities` wraps, so the public function keeps its signature, its checks, its order and its answers; the token functions run the same core inside their own transaction, which also re-checks under lock that the pair is still pending and that neither entity has been merged away, writes the review row as merged with `decided_token`, the ledger row with `merge_id`, and the audit row with `audit::record_on`. The follow-up steps run after commit as today; a failure there is returned in `follow_up_error` of an `applied` outcome, never as an error. `merge_entity_pair` takes the caller's source and target and, when the two entities have a pending review of their own, closes it as merged with the token recorded.
- Gate before merge (N1 below): `merge_duplicate_pair` and `merge_entity_pair` call `hold_for_token_merge` and then `agent_policy(AgentOperation::Merge, hold)` before the transaction opens; a hold, or `breaker` true, writes one proposal row plus its `agent.proposal` audit row and touches no fact, entity, evidence or review row. The unique index decides a race: the loser reads the existing row and returns it with `existing` true.
- Token revert: `token_agent_actions::revert_merge` calls `resolution::revert_merge` unchanged when the ledger shows a token agent made the merge, then writes the `merge.revert` ledger row and audit row; for any other merge, or with `breaker` true, it writes a proposal (`merge_by_person` when `entity_merges` names a user, `merge_by_governor` otherwise, `breaker`). `resolution::revert_merge` owns its own transaction and is not changed, so the revert and its two rows cannot share one transaction: write them so that a failure after the revert is retried or surfaced, and record in the Log what a reader sees if the process dies between the two.
- Lost races map to `already_decided`: a decided or missing-pending review, "Entity already merged", "Merge already reverted". A pair locked by a running governor round returns what `keep_duplicate_pair` returns for it.
- Precedent (E25, proved again end to end by T006): change `governance::type_pair_stats` so a merge made by a token agent and reverted by a token is not counted as reverted; a person's revert of a token merge still counts. Check `precedents_for`, `decided_before`, `gate` and `settled_by_people`: a live token merge must count in none (a review row merged with `decided_token` set is not a person's decision).
- Existing tests this task owns (lesson 1): in `crates/utopia-store/tests/a_token_keep_is_never_human_precedent.rs`, `replaying_migration_0128_changes_nothing` changes only its column assertion, from the exact list to "contains every column 0128 created", because 0129 adds columns; `the_compiled_table_holds_the_owners_ruling` keeps every assertion (the signature of `agent_policy` does not change). No other existing test is edited.
- State comparison (E12, proved again over the API by T003): the test compares every `facts` row of the base, every `entities` row except `updated_at`, and every `fact_evidence` and `typed_fact_sources` row, before the merge and after the revert, on typed entities.
- N1 (judgment prohibition, SC1). Must not: let any token merge reach the merge without the server gate being asked first. Detail: the reviewer checks that every token merge entry, queue decision, manual merge and batch member, each over REST and MCP, calls the gate before the merge, and that no token caller reaches the session branch's ungated code. Here: both token merge functions ask the gate themselves, so no caller can skip it.
- N2 (judgment prohibition, SC1). Must not: report a merge as failed, or leave it without its ledger and audit rows, when the entities were merged. Detail: the reviewer checks that the ledger row naming the merge and the audit row are written with the merge, and that a failure of a later follow-up step is reported on an `applied` result.
- Conventions (bind this task): Chinese explanatory comments; sentence-named tests; English user-facing strings, each refusal with a stable code; one behaviour-sentence commit subject; DCO sign-off is deferred to the upstream submission; nothing is sent to `deeplethe/utopia` or a deployed instance. Tests seed through store functions or direct inserts, never through model jobs.

## Interface contract

- **Ledger (delivered by T001).** Migration `migrations/0129_a_token_agent_action_keeps_its_reason_its_batch_its_merge_and_its_later_state.sql` adds to `token_agent_actions`, all nullable: `gate_reason TEXT`, `batch_id UUID`, `merge_id UUID`, `target_key TEXT`, `state TEXT` (checked: `approved`, `declined`, `superseded`, `undone`), `state_at TIMESTAMPTZ`, `state_by UUID`; and the partial unique index `token_agent_actions_open_proposal_idx` on `(kb_id, operation, target_key)` where `outcome IN ('held','proposed') AND state IS NULL`. `CURRENT_SCHEMA_VERSION` is 115. The ledger `operation` and the audit `action` share one name: `review.keep`; `review.merge` (`target_kind` `review`, `target_id` and `target_key` the review id); `merge.manual` (`target_kind` `entity`, `target_id` the target entity, `target_key` the two entity ids in ascending order joined by `|`); `merge.revert` (`target_kind` `merge`, `target_id` and `target_key` the merge id). `outcome` is `applied`, `held` (a gate hold) or `proposed` (propose only). `gate_reason` is one of `identity`, `contradiction`, `derived`, `answered`, `kept_by_person`, `reverted_merge` (with `held`) or `merge_by_person`, `merge_by_governor`, `breaker` (with `proposed`). `merge_id` on an `applied` merge row is the merge it made, on a `merge.revert` row the merge it targets, on an `approved` merge proposal the merge the person's approval made. `payload` holds the full request. An open proposal is a row with outcome `held` or `proposed` and `state` null. `approved`, `declined` and `superseded` are stored by the answer route with `state_at` and `state_by` (the answering person). `undone` is never stored: an `applied` merge row reads `state` `undone`, with `state_at` the revert time, whenever `entity_merges.reverted_at` of its `merge_id` is set, so a person's revert through today's unchanged handler shows it with no write. A merge made by a token agent is a merge named by `merge_id` of a row with operation `review.merge` or `merge.manual` and outcome `applied`; a merge reverted by a token is one named by an `applied` `merge.revert` row; every other reverted merge was reverted by a person or the governor's fuse.
- **Audit rows of token writes (delivered by T001).** Written in the transaction of the ledger row, `actor_id` the token's owner, detail carrying `token_id`, `token_name`, `action_id` (the ledger row), `merge_id` when a merge is named and `batch_id` when the call is a batch member: `review.merge`, `merge.manual` and `merge.revert` for an applied call (target the review, the target entity, the merge), and `agent.proposal` (`target_kind` `agent_action`, target the ledger row, detail also `operation`, `outcome`, `reason`) for a held or propose-only call.
- **Store functions (delivered by T001; no later task changes a signature).** In `utopia_store::execution_gate`: `Hold` gains the variants `KeptByPerson` and `RevertedMerge` and the method `Hold::code(&self) -> &'static str` returning the `gate_reason` code; `hold_for_token_merge(pool: &PgPool, kb_id: Uuid, a: Uuid, b: Uuid) -> AppResult<Option<Hold>>` asks `hold_for_merge` first, then the kept-pair lookup, then the reverted-merge lookup, both by entity ids in either order. `hold_for_merge`, `agent_ruling` and the signature of `agent_policy` are unchanged, and `hold_for_merge` never returns a new variant. In `utopia_store::token_agent_actions`: `pub struct TokenWrite { pub kb_id: Uuid, pub owner_id: Uuid, pub token_id: Uuid, pub rationale: Option<String>, pub batch_id: Option<Uuid>, pub breaker: bool }`; `pub struct TokenWriteOutcome { pub action: TokenAgentAction, pub existing: bool, pub follow_up_error: Option<String> }` (`existing` is true when the call met an open proposal and wrote nothing; `follow_up_error` is set when the merge committed and a later follow-up step failed); `merge_duplicate_pair(pool: &PgPool, w: &TokenWrite, review_id: Uuid) -> AppResult<TokenWriteOutcome>`, `merge_entity_pair(pool: &PgPool, w: &TokenWrite, source: Uuid, target: Uuid) -> AppResult<TokenWriteOutcome>` and `revert_merge(pool: &PgPool, w: &TokenWrite, merge_id: Uuid) -> AppResult<TokenWriteOutcome>`. Each asks the gate or the propose-only rule itself before it writes; with `breaker` true a merge or a revert lands `proposed` with reason `breaker`. Errors: `AppError::NotFound` (unknown id or another base); `AppError::CodedConflict` with code `already_decided` (decided pair, lost race, entity already merged away, merge already reverted); `AppError::Invalid` with code `self_merge`; the uncoded `AppError::Conflict` that `keep_duplicate_pair` returns for a pair a running governor round holds. `TokenAgentAction` gains `gate_reason`, `batch_id`, `merge_id`, `state`, `state_at`, `state_by`; an Agent History ledger row gains the keys `reason`, `batch_id`, `merge_id`, `state`, `state_at`, each present only when it has a value, so the row of a keep has exactly the keys it has today. `resolution::merge_entities` and `resolution::revert_merge` keep their signatures and behaviour. `governance::type_pair_stats` no longer counts, as reverted, a merge made by a token agent and reverted by a token.

## Acceptance criteria

1. Migration 0129 adds the seven columns and the partial unique index of the Interface contract, a second run changes no schema, `CURRENT_SCHEMA_VERSION` is 115 and `cargo test -p utopia-cli` passes.
2. A token merge the gate passes writes, in one transaction, the merge, the review row (`merged`, `decided_token` set), one `applied` ledger row naming the merge and one audit row with `token_id` and `token_name`; with a token id that has no name to snapshot nothing is merged and no row is written (N2).
3. A follow-up failure after the merge commits is returned as `follow_up_error` on an `applied` outcome whose ledger and audit rows exist (N2).
4. Each of the six holds (identity, contradiction, derived, answered, a pair a person kept, a pair with a reverted merge) lands one proposal whose `gate_reason` names it, for `merge_duplicate_pair` and `merge_entity_pair`, and the facts, entities, evidence and review rows of the base are equal before and after; the two new holds are found by entity ids in either order; a pair a token kept is not held.
5. A repeated held call, and two held calls sent at once, leave one open proposal and return its id with `existing` true.
6. A token merge followed by its token revert leaves `facts`, `entities` (without `updated_at`), `fact_evidence` and `typed_fact_sources` of the base equal to their state before the merge; a second revert is `already_decided`; a token revert of a merge a person or the governor made writes a proposal and reverts nothing.
7. Of two callers merging one pair at once exactly one merge exists afterwards and a losing token call gets `already_decided`; `resolution::merge_entities` and `resolution::decide_review` called as a person calls them answer as before (the six named existing store tests pass).
8. A live token merge, and a merge made and reverted by tokens, change the result of no governor precedent read (`precedents_for`, `type_pair_stats`, `decided_before`, `gate`, `settled_by_people`) and queue no govern round; a person's revert of a token merge counts in `type_pair_stats` as any revert does.
9. `hold_for_merge` returns only its four existing holds, and the server crate compiles against the changed store.
