# T004 — Open fact confirm, reject and close and conflict resolution to a token as proposals

## Context

T002 delivered the propose path, the answer dispatch and the defect family; T003 shows proposals on cards. This task adds the four operations of Unconfirmed, Low confidence and Conflicts. The M003 patterns to follow are in `crates/utopia-server/src/api/review_routes.rs` and `crates/utopia-server/src/api/review_ops.rs`: the token branch of `review_routes::decide` (lines 353 to 374), `review_ops::authorize_write` (lines 69 to 84), `review_ops::keep` (lines 361 to 388), `review_ops::guard` (lines 317 to 344) and the answer dispatch `review_routes::answer_proposal` (lines 850 to 918). The session handlers are `confirm_fact`, `reject_fact`, `close_fact` (`crates/utopia-server/src/api/review_routes.rs` line 252, body `CloseFactBody` line 225, precision check `world_precision` line 236) and `resolve_conflict` (line 313, body `ConflictBody` line 295, store call `temporal::resolve_review_conflict`). Their routes are declared in `crates/utopia-server/src/api/mod.rs` lines 610 to 628. `close_fact` answers 404 for a fact that is not live and open-ended, and its store call `temporal::close_superseded` can report that it changed nothing.

## Approach

- For each handler: take `SessionOrToken`, branch on the token as T002 did for `decide_defect`, and move the session statements unchanged into one function that takes the person and an optional proposal id. Add one `answer_proposal` arm per operation string.
- The body checks a person gets are given at propose time and land nothing: `bad_precision`, a close without a usable date (`close_at_required`), an inverted interval (`interval_inverted`) and the store's refusal of an unknown conflict action. Checks that need the target's state run after `target_open`.
- A conflict proposal stores the conflict's two fact ids as `fingerprint`; approval supersedes it when they differ. An approved close whose store call reports no change is `superseded`.
- Replace `a_token_is_still_refused_on_the_fact_confirm_route`, `..._fact_reject_route` and `..._conflict_route` with the new behaviour; the bodies those tests sent do not match the request structs and are not kept.
- N2 (judgment): each approval is applied with the person as actor and its audit detail names the proposal. N3 (judgment): no new entry answers a proposal.
- MCP: follow the M003 write tools in `crates/utopia-server/src/api/review_tools.rs` (`serves` line 39, `writes` line 44, `definitions` line 70, `annotations` line 358, `listed` line 378, `bad_argument` line 403, `call` line 487). `crates/utopia-server/src/api/mcp.rs` calls only `listed`, `serves` and `call` and is not edited. ## Interface contract

- **Typed target state (delivered by T001).** New module `crates/utopia-store/src/review_targets.rs`: `pub enum TargetState { Open, Decided, Missing }`; `pub async fn target_state(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid, request: &serde_json::Value, fingerprint: Option<&serde_json::Value>) -> AppResult<TargetState>`; `pub async fn fingerprint(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid) -> AppResult<Option<serde_json::Value>>`; `pub async fn target_label(pool: &PgPool, kb_id: Uuid, operation: &str, target_id: Uuid, request: &serde_json::Value) -> AppResult<String>`; `pub async fn ontology_proposal_id(pool: &PgPool, kb_id: Uuid, section: &str, key: &str) -> AppResult<Option<Uuid>>`. Every read is scoped by base, so an id of another base is `Missing`, and no error text is matched. Rules: `fact.confirm` — a missing or invalidated fact is `Missing` and there is no `Decided`; `fact.reject` and `fact.close` — an invalidated fact is `Decided`, and for `fact.close` a live fact that already has an end is `Missing`; `conflict.resolve` — `Open` while the conflict's status is open and both facts are live, `Decided` otherwise, and `Decided` when a fingerprint is given and the conflict's two fact ids differ from it; `violation.decide` — `Open` while the violation's status is open and, for the resolutions `fact_retracted` and `fact_closed`, the fact the request names is live and has no end, `Decided` otherwise; `defect.decide` — `Open` while the defect's status is open; `errata.decide` — `Open` while the action's status is held; `ontology.proposal` — `Open` while the proposal's status is open and the ontology agent proposed it, and `Decided` when a fingerprint is given and the stored payload differs from it; `alignment.phrase`, `alignment.rule` and `pending.nod` — `Open` while the row exists and `Missing` otherwise, with no `Decided`; `governor.answer` — `Open` when the decision is `proposed` and its review row is still pending, or the decision is `applied`, and `Decided` otherwise; `mapping.decide` — `Decided` when the mapping's status equals the requested status and `Open` otherwise. `fingerprint` returns the conflict's two fact ids or the ontology proposal's stored payload, and nothing for any other operation.

Order in a family function: `authorize_write`; shape checks of the body with the person's codes; `target_open`; the state-dependent checks with the person's codes; `land_proposal`. Answer, HTTP 200: `{"ok":true,"outcome":"proposed","action_id":…,"reason":"propose_only","explanation":…}` plus `"code":"already_proposed"` only when the call met the open proposal, whose id `action_id` then is. Refusals: 403 `token_read_only`, 403 `token_kb_out_of_scope`, 403 `token_owner_below_editor` (checked in that order, as `authorize_write` does today), 404, 409 `already_decided`, and the person's 422 codes. - **Proposal answer for every operation (delivered by T002; each family task adds its arm).** The two session-only routes `POST /api/v1/kbs/{id}/review/agent-proposals/{proposal_id}` and `POST /api/v1/kbs/{id}/review/agent-proposals` keep `AuthUser`, their bodies and their M003 answers; `review_routes::answer_proposal` gains one arm per operation string and keeps answering 500 for an operation it does not know. ## Acceptance criteria

1. Over REST and over `review_fact`, confirm, reject and close of a seeded fact by a write token of an editor each answer `proposed`, change no fact, entity, evidence row or queued job, and leave one open proposal per operation.
2. E2 (held-out; ruling: one open proposal per base, operation and target; a repeat or a second call at the same moment returns the existing proposal's id with `already_proposed` and writes no second row; two different operations on one target may both be open): a repeated call and two simultaneous calls return one id, and confirm and reject of one fact are both open.
3. A signed-in editor approves each kind and the facts change exactly as that person's own confirm, reject, close or conflict resolution changes them, with the person as actor and the proposal named in the audit detail; a declined proposal changes nothing.
4. E8 (held-out; ruling: approving a proposal whose target is gone or was decided meanwhile closes it as `superseded`, changes nothing else and the answer says so; for a target with no decided state approval applies the decision while the target exists): a reject or close proposal on a fact invalidated meanwhile, and a conflict proposal whose conflict was resolved or whose facts changed, answer `superseded`; a confirm proposal on a live fact applies.
5. Over REST and over `review_conflict`, each of the four conflict actions waits as a proposal; an unknown action, a missing close date and an inverted interval get the person's refusal and land nothing.
6. The session answers of the four routes are unchanged, and `review_fact` and `review_conflict` are listed and refused as the write tools are.
