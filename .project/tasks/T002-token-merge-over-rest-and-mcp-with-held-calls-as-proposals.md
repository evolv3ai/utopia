# T002 — A write token of an editor merges a duplicate pair or two entities over the token API and MCP behind the gate, and a held call lands one proposal

## Context

The walking skeleton of M003: one gated merge end to end. T001 delivered the store side (`token_agent_actions::merge_duplicate_pair` and `merge_entity_pair`, the six-hold gate, proposals with one open row per target). This task opens the two merge routes and the MCP merge tool on top of it. Ground truth at `6c52ce8`: `review_routes::decide` (351 to 420) takes `SessionOrToken`; its token branch runs `review_ops::keep` for `keep` and answers every other action with `authorize_write` then `not_open()` (403 `token_operation_not_open`). `review_routes::manual_merge` (737) takes `AuthUser`, calls `resolution::merge_entities`, writes audit `merge.manual` and answers the merge id; a token gets 401. `review_ops.rs` holds `ReviewCaller`, `authorize_write` and `keep`, the model for a token write (authorize, policy, store function, `state.emit_review`, no `after_human_decision`). `review_tools.rs` holds the three tools; `listed(can_write)` filters `review_keep` by name, and `serves`, `definitions`, `annotations` and `call` each name the tools. Existing tests assert the refusals this task lifts: `review_token_api_tests.rs::a_refused_token_merge_revert_or_batch_leaves_the_graph_equal` (295; merge 403 `token_operation_not_open` at 351 to 352, `/entities/merge` 401 inside 354 to 375, the file header at lines 11 to 12) and `review_mcp_reads_tests.rs::the_mcp_endpoint_offers_no_review_tool_beyond_list_item_and_keep` (1039; exact tool lists 1048 to 1063, the read-only annotation loop 1073 to 1082, `review_merge` answered -32601 at 1149 to 1168). The server crate has no `lib.rs`: tests are sibling files declared in `crates/utopia-server/src/api/mod.rs` (676 to 710).

## Approach

- Routes: `decide` keeps its extractor; in its token branch `merge` goes to `review_ops::merge_pair`, `keep` stays, any other action stays `token_operation_not_open`. `manual_merge` changes extractor to `SessionOrToken` and sends a token caller to `review_ops::merge_entities`.
- The session branch is not rewritten. In each handler whose extractor changes to `SessionOrToken`, a session caller runs the statements that are there today, in the same order, and gets the same answer; a token caller leaves the handler for `review_ops` before any of them. `resolution::revert_merge` is not changed by any task.
- `review_ops`: both functions call `authorize_write` first (scope, then Editor), build a `TokenWrite` with `breaker: false` and the `batch_id` they were given, call the T001 store function, call `state.emit_review`, and shape the answer of the Interface contract. They never call `governance::after_human_decision` and never call `resolution::decide_review` or `resolution::merge_entities` directly.
- MCP: add `review_merge` to `serves`, `definitions`, `annotations` (not read-only), the write filter of `listed` and `call`; it calls the same two `review_ops` functions. A refusal goes through the existing `refusal` mapping so the tool error carries the REST code.
- Existing tests this task changes (lesson 1). In `review_token_api_tests.rs`: rename `a_refused_token_merge_revert_or_batch_leaves_the_graph_equal` to `a_token_refused_on_merge_manual_merge_revert_or_batch_leaves_the_graph_equal`, a name that stays true for the whole milestone; replace the two assertions this task lifts (queue merge 403 `token_operation_not_open`; `/entities/merge` 401) with refusals that remain (a `read` token gets `token_read_only`, a `write` token of a Viewer gets `token_owner_below_editor`, on both merge routes); leave the batch and revert assertions (401) exactly as they are, T003 and T005 lift those; keep the graph-equal and empty-ledger checks; correct the file header. In `review_mcp_reads_tests.rs`: rename `the_mcp_endpoint_offers_no_review_tool_beyond_list_item_and_keep` to `the_mcp_endpoint_offers_exactly_the_review_tools_the_ruled_table_opens`; add `review_merge` to the write token's expected list and annotation expectations; the -32601 probe moves from `review_merge` to names that stay unknown (`review_decide`, `review_confirm`, `review_approve`). Every other assertion in both files keeps its expectation (E24). T003 and T005 edit these two tests again and must keep both names.
- New tests go in `crates/utopia-server/src/api/review_token_merge_tests.rs` (declare it in `crates/utopia-server/src/api/mod.rs`), built on `review_session_unchanged_tests::Fx`. The concurrency test (E2) runs a session merge, a governor decision and a token merge of one pair together and asserts one `entity_merges` row and `already_decided` for a losing token; a pair held by a running governor round gets the same 409 the keep gets.
- N1 (judgment prohibition, SC1). Must not: let any token merge reach the merge without the server gate being asked first. Detail: the reviewer checks that every token merge entry, queue decision, manual merge and batch member, each over REST and MCP, calls the gate before the merge, and that no token caller reaches the session branch's ungated code. Here: both routes and the tool reach the merge only through the two T001 store functions, which ask the gate.
- N2 (judgment prohibition, SC1). Must not: report a merge as failed, or leave it without its ledger and audit rows, when the entities were merged. Detail: the reviewer checks that the ledger row naming the merge and the audit row are written with the merge, and that a failure of a later follow-up step is reported on an `applied` result. Here: `follow_up_error` is passed through on a 200 `applied` answer.
- Conventions (bind this task): Chinese explanatory comments; sentence-named tests; English user-facing strings, each refusal with a stable code; one behaviour-sentence commit subject; DCO sign-off is deferred to the upstream submission; nothing is sent to `deeplethe/utopia` or a deployed instance. Tests seed through store functions or direct inserts, never through model jobs.

## Interface contract

- **Ledger (delivered by T001).** Migration `migrations/0129_a_token_agent_action_keeps_its_reason_its_batch_its_merge_and_its_later_state.sql` adds to `token_agent_actions`, all nullable: `gate_reason TEXT`, `batch_id UUID`, `merge_id UUID`, `target_key TEXT`, `state TEXT` (checked: `approved`, `declined`, `superseded`, `undone`), `state_at TIMESTAMPTZ`, `state_by UUID`; and the partial unique index `token_agent_actions_open_proposal_idx` on `(kb_id, operation, target_key)` where `outcome IN ('held','proposed') AND state IS NULL`. `CURRENT_SCHEMA_VERSION` is 115. The ledger `operation` and the audit `action` share one name: `review.keep`; `review.merge` (`target_kind` `review`, `target_id` and `target_key` the review id); `merge.manual` (`target_kind` `entity`, `target_id` the target entity, `target_key` the two entity ids in ascending order joined by `|`); `merge.revert` (`target_kind` `merge`, `target_id` and `target_key` the merge id). `outcome` is `applied`, `held` (a gate hold) or `proposed` (propose only). `gate_reason` is one of `identity`, `contradiction`, `derived`, `answered`, `kept_by_person`, `reverted_merge` (with `held`) or `merge_by_person`, `merge_by_governor`, `breaker` (with `proposed`). `merge_id` on an `applied` merge row is the merge it made, on a `merge.revert` row the merge it targets, on an `approved` merge proposal the merge the person's approval made. `payload` holds the full request. An open proposal is a row with outcome `held` or `proposed` and `state` null. `approved`, `declined` and `superseded` are stored by the answer route with `state_at` and `state_by` (the answering person). `undone` is never stored: an `applied` merge row reads `state` `undone`, with `state_at` the revert time, whenever `entity_merges.reverted_at` of its `merge_id` is set, so a person's revert through today's unchanged handler shows it with no write. A merge made by a token agent is a merge named by `merge_id` of a row with operation `review.merge` or `merge.manual` and outcome `applied`; a merge reverted by a token is one named by an `applied` `merge.revert` row; every other reverted merge was reverted by a person or the governor's fuse.
- **Audit rows of token writes (delivered by T001).** Written in the transaction of the ledger row, `actor_id` the token's owner, detail carrying `token_id`, `token_name`, `action_id` (the ledger row), `merge_id` when a merge is named and `batch_id` when the call is a batch member: `review.merge`, `merge.manual` and `merge.revert` for an applied call (target the review, the target entity, the merge), and `agent.proposal` (`target_kind` `agent_action`, target the ledger row, detail also `operation`, `outcome`, `reason`) for a held or propose-only call.
- **Store functions (delivered by T001; no later task changes a signature).** In `utopia_store::execution_gate`: `Hold` gains the variants `KeptByPerson` and `RevertedMerge` and the method `Hold::code(&self) -> &'static str` returning the `gate_reason` code; `hold_for_token_merge(pool: &PgPool, kb_id: Uuid, a: Uuid, b: Uuid) -> AppResult<Option<Hold>>` asks `hold_for_merge` first, then the kept-pair lookup, then the reverted-merge lookup, both by entity ids in either order. `hold_for_merge`, `agent_ruling` and the signature of `agent_policy` are unchanged, and `hold_for_merge` never returns a new variant. In `utopia_store::token_agent_actions`: `pub struct TokenWrite { pub kb_id: Uuid, pub owner_id: Uuid, pub token_id: Uuid, pub rationale: Option<String>, pub batch_id: Option<Uuid>, pub breaker: bool }`; `pub struct TokenWriteOutcome { pub action: TokenAgentAction, pub existing: bool, pub follow_up_error: Option<String> }` (`existing` is true when the call met an open proposal and wrote nothing; `follow_up_error` is set when the merge committed and a later follow-up step failed); `merge_duplicate_pair(pool: &PgPool, w: &TokenWrite, review_id: Uuid) -> AppResult<TokenWriteOutcome>`, `merge_entity_pair(pool: &PgPool, w: &TokenWrite, source: Uuid, target: Uuid) -> AppResult<TokenWriteOutcome>` and `revert_merge(pool: &PgPool, w: &TokenWrite, merge_id: Uuid) -> AppResult<TokenWriteOutcome>`. Each asks the gate or the propose-only rule itself before it writes; with `breaker` true a merge or a revert lands `proposed` with reason `breaker`. Errors: `AppError::NotFound` (unknown id or another base); `AppError::CodedConflict` with code `already_decided` (decided pair, lost race, entity already merged away, merge already reverted); `AppError::Invalid` with code `self_merge`; the uncoded `AppError::Conflict` that `keep_duplicate_pair` returns for a pair a running governor round holds. `TokenAgentAction` gains `gate_reason`, `batch_id`, `merge_id`, `state`, `state_at`, `state_by`; an Agent History ledger row gains the keys `reason`, `batch_id`, `merge_id`, `state`, `state_at`, each present only when it has a value, so the row of a keep has exactly the keys it has today. `resolution::merge_entities` and `resolution::revert_merge` keep their signatures and behaviour. `governance::type_pair_stats` no longer counts, as reverted, a merge made by a token agent and reverted by a token.
- **Token merge over REST (delivered by T002).** `POST /api/v1/kbs/{kb_id}/review/{review_id}` with body `{"action":"merge","rationale":"…"}` and `POST /api/v1/kbs/{kb_id}/entities/merge` with body `{"source":"…","target":"…","rationale":"…"}` take `SessionOrToken`; `rationale` is optional. A token caller goes to `review_ops::merge_pair(state, caller, review_id, rationale, batch_id)` or `review_ops::merge_entities(state, caller, source, target, rationale)`, both `pub(crate) async` and returning `Result<serde_json::Value, AppError>`. Answers, HTTP 200: applied `{"ok":true,"outcome":"applied","action_id":…,"merge_id":…}` plus `"follow_up_error"` (a string) only when a follow-up step failed after the merge; held or propose only `{"ok":true,"outcome":"held"|"proposed","action_id":…,"reason":…,"explanation":…}` plus `"code":"already_proposed"` only when the call met the open proposal, whose id `action_id` then is. Refusals: 403 `token_read_only`, 403 `token_owner_below_editor` (scope checked first), 404, 409 `already_decided`, 409 with no code for a pair a running governor round holds, 422 `self_merge`, 403 `token_operation_not_open` for an action other than `keep` or `merge` on the decision route. A session caller of either route runs today's code and gets today's answers.
- **MCP write tools (file `crates/utopia-server/src/api/review_tools.rs`).** Listed in `tools/list` and callable only for a `write` token whose owner is at least Editor, each annotated `readOnlyHint: false`; a caller without that right that calls one gets a tool error with the REST code. `review_merge` (T002): `id` (a pending duplicate pair) or `source` and `target` (entity ids), optional `rationale`; `structuredContent` is the REST body of the matching merge route. `review_revert` (T003; `batch_id` added by T005): exactly one of `merge_id` and `batch_id`, optional `rationale`; `structuredContent` is the REST body of the revert route or of the unit revert; its description says that a revert restores graph state only and does not recall derivations, violations, exports or answers drawn while the merge was live, and that a target that had no type before the merge keeps the type it took. `review_batch` (T005): `ids`, `action` (`merge` or `keep`), optional `rationale`; `structuredContent` is the REST body of the token batch. A refused call is a tool result with `isError: true` and `structuredContent` `{"code","message"}` carrying the REST code (`not_found` for a 404). No tool answers a proposal: a call to any other `review_` name is JSON-RPC error -32601.

## Acceptance criteria

1. SC1: a `write` token of an Editor merges a pair the gate passes with `POST /review/{review_id}` and, for a second pair, with the MCP tool `review_merge`: the entities are merged, the answer names `merge_id`, one ledger row with outcome `applied` and that `merge_id` exists, and the audit row carries `token_id` and `token_name`.
2. SC2 and E7 (criterion SC2): the same call on a held pair answers 200 with outcome `held` and the gate's reason, lands one open proposal, and the facts, entities, evidence and review rows of the base are equal before and after; a repeat answers with `code` `already_proposed`.
3. E1 (held-out; ruling: a token merge of a pair that is already decided, by anyone, answers `already_decided`; no second merge happens and no second `applied` ledger row is written).
4. E2 (held-out; ruling: when a person, the governor and a token decide one pair at once exactly one decision is applied and a losing token call answers `already_decided`, not a not-found or an uncoded conflict; a pair locked by a running governor round gets the refusal the M001 keep returns for it today).
5. E3 (held-out; ruling: a token manual merge of an entity with itself keeps the existing `self_merge` refusal; an entity already merged into another answers `already_decided`; an entity id that is unknown or belongs to another base is not found; none of these lands a proposal or changes the graph).
6. E4 (held-out; ruling: a token queue merge merges in the direction the person's queue merge takes for that pair; a token manual merge takes the caller's source and target, and when it applies it closes that pair's own pending review as merged with the token recorded).
7. E5 (held-out; ruling: each of the six hold reasons lands a proposal whose reason names that hold; the kept-pair and reverted-merge holds are looked up by entity ids, in either order, for the queue merge and the manual merge alike).
8. E6 (held-out; ruling: one open proposal per base, operation and target; a queue merge's target is its review id and a manual merge's target is the unordered pair of entity ids; a repeat, or a second call arriving at the same moment, returns the existing proposal's id with `already_proposed` and writes no second row).
9. `review_merge` is listed only for a `write` token of an Editor; called by a `read` token or a Viewer's token it returns a tool error with `token_read_only` or `token_owner_below_editor`; `review_decide`, `review_confirm` and `review_approve` are JSON-RPC -32601.
10. A token merge queues no govern round and calls no `after_human_decision`; a signed-in editor's queue merge and manual merge of a pair the gate would hold are applied as today (`review_session_unchanged_tests` passes unedited).
11. The two renamed existing tests pass with only the assertions named in the Approach changed; the batch and revert refusals in them are untouched.
